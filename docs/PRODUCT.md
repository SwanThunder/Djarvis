## Purpose and audience

A commercial personal task and habit tracker with a conversational, voice-controlled butler/secretary. Initial customers are individual users managing personal responsibilities and professionals with busy schedules. Team, family, and organization workspaces are not part of the current stated audience.

The central value is simpler planning: users create and update tasks and habits by voice, hear their daily plan at a chosen time or situation, and ask for weather or internet information.

## Platforms and scope

Develop for Windows 10 and 11 first; subsequently design Android and cross-device synchronization. The target is 8 GiB RAM and does not require a discrete GPU; this target is not yet a validated minimum. CPU performance and compatibility with local models must be tested. Do not claim that the current 4B development model has been validated for CPU-only use with 8 GiB RAM. A compact installer downloads suitable local model(s) at first launch based on the device's hardware. Model profiles may use a coarse local RAM/CPU/GPU capability assessment for model selection, not as a trial fingerprint. User data is stored on the device; cloud storage and cross-device synchronization are later capabilities, and their design is open. AI inference in the current release must be local only; cloud AI inference is excluded. With valid trial/license access and required local resources available, local planner sections, reminders, voice, and conversation work offline. Search, live weather, and external providers require a network connection.

The owner described installation as “hidden.” For product UX, this is interpreted as setup running automatically or in the background without a console or manual commands, while an in-app preparation status makes progress visible and avoids an apparent hang. This is an interpretation of the requested experience, not a confirmed implementation detail or permission for invisible system installation or data collection.

The application uses a local profile with no mandatory in-app account. A buyer imports a signed license file, which the application verifies offline; there is no own activation/subscription server or server-side entitlement registration. Future account or identity needs for cloud synchronization remain a separate design question. The seven-day full-product trial is per device and starts on first use of any product function, including the manual planner; setup screens and waiting for model downloads do not start it. The application remembers the device to deter repeated trials through alternate accounts. This is not a claim to uniquely identify a person or provide unbypassable local licensing. No device fingerprint was collected during environment preparation; hardware capability assessment for model selection is separate from the trial mechanism. License format, signing algorithm/issuer, payment and renewal details, device binding, and clock tolerance remain unresolved. After trial or subscription expiry, planner and assistant functions are locked and data is retained. Renewal/import, user-initiated data deletion, and automatic backups remain available; all microphone capture and proactive speech stop.

The owner wants the entire requested product designed without a deadline or arbitrary feature cuts. Implementation order will follow dependencies and explicit approval; an implementation sequence does not remove features from the target scope.

## Required capabilities

### Tasks and planning

- A task cannot be created without a title and an explicitly selected priority (low, normal, high, or urgent); if priority is missing, ask the user rather than defaulting to normal. Description, project, deadline, scheduled time, duration, recurrence, and reminders are optional; completion is tracked. A task with no duration can be saved. A manually entered start time with unknown duration is a start-only marker, not a busy interval or `SchedulePlacement`; ask for duration before automatic planning. Advanced subtasks, checklists, tags, and attachments are controlled by a global setting, and can be expanded independently on each task. Hiding advanced fields never deletes their data.
- Calendar, recurring tasks, and projects.
- Automatic day planning.
- Voice creation and modification of tasks, habits, and their records.
- Daily spoken plans triggered by user-configured times or situations.

The automatic day planner considers meetings, deadlines, priorities, durations, habits, breaks, and the user's available hours. Automatic breaks are inserted only after the user specifies both their duration and frequency; until configured, the planner adds no automatic breaks. It proposes a plan and applies it after confirmation or remembered permission. Manually placed task times stay locked unless the user explicitly permits changing them. Task splitting is allowed only when the user opts in for that task; the planner never silently splits work. Segment check-offs record progress only; completing every segment does not complete the task. The selected task occurrence completes only through a separate task-completion action; this proposal maps that action to `CompleteOccurrence`, but the exact API name is not approved. It can be issued even if not every segment is checked off. Elapsed schedule slots are never proof of completion. Completing one occurrence does not complete other historical or future occurrences. What happens to remaining planned segments/slots after completion remains to be designed. An overdue deadline and a missed scheduled time are distinct states and are displayed separately. A missed scheduled time is highlighted and announced aloud; its date is not changed automatically. Whether a per-task override is available remains unresolved. Recurrence follows its original schedule even when an occurrence is completed late: a task due November 1 every seven days and completed November 3 is next due November 8, not November 10. Missed occurrences remain separate outstanding debt. For monthly recurrence rules whose scheduled day does not exist in a month, the per-rule behavior is configurable; the default is the last day of that month, with skipping also available. Keep the original anchor day: January 31 → February 28 → March 31, not March 28. For a planning date with no time, the allowed placement window is 06:00–22:00, using the task's own duration; this is not a 16-hour duration or global workday. An explicit deadline date without a time always prompts the user for a time on each entry; do not assign midnight or 22:00 automatically. Each habit and personal recurrence has a choice to follow local time or retain its original fixed time zone. If unset, ask when the user's time zone changes. Do not implicitly apply this choice to externally scheduled meetings or retime historical records. Exact DST, transition and storage mechanics remain to be designed. Other conflict rules still need design. Ambiguous commands always require clarification of the target, even when task-change confirmations are disabled (for example, which of several meetings to move). Clarification resolves what the user means; it is separate from optional confirmation before acting.

### Habits

- Four habit types: yes/no completion, quantity, duration, and abstaining from an undesired behavior.
- Both fixed-day schedules and flexible frequency schedules, such as three times per week. Flexible frequency counts distinct successful days; multiple logs on one day may contribute to measurements but count as at most one successful day toward weekly frequency.
- Completion tracking and statistics. Missed occurrences remain misses in statistics and do not accumulate as task-like debt.
- Personalized plans, analysis of missed habits, and gradual goal increases or workload changes proposed by the assistant. The assistant never applies goal or load changes without user approval; the task-change no-confirmation preference does not override this restriction.
- Users choose and configure which of these behaviors are active.

Habit weeks start Monday. If a pause leaves fewer eligible days than the quota for a flexible habit, mark that week paused: it is neither a miss nor a streak break, and does not trigger automatic goal reduction. A fixed-schedule streak counts successful scheduled days; unscheduled and paused days do not break it. A flexible-schedule streak counts successful weeks; paused weeks are frozen. Corrections may be backdated to any past date during the habit's lifetime, but not before it existed or as a future actual success. Preserve correction history and recalculate historical statistics using the goal that applied then. Exact storage/audit representation and statistics implementation remain proposed.

### Assistant and interface

- Main screen: a futuristic circular visualization of the assistant, inspired by the cinematic JARVIS presentation, and a day dashboard below it.
- Required visual direction: dark Glassmorphism with an asymmetric Bento layout, a left sidebar, and a top bar. Proposed section groupings and panel placement map only to existing tasks, calendar, habits, projects, and notes; these details and the default theme remain proposals. Do not add CRM-specific entities or invented demo data. See [visual design requirements](DESIGN.md).
- Required appearance controls: the exact palettes `deep-blue-pink` (`#09318D`, `#FFFFFF`, `#F59ACC`), `pink-orange` (`#DB3996`, `#FC734D`, `#F59ACC`), and `midnight-electric` (`#0A1430`, `#0297DE`, `#FC734D`), plus independent Glass/Solid modes. Solid surfaces are fully opaque, including nested surfaces; no background image is used. One appearance section in existing settings shows color swatches and a separate transparency control, applies changes immediately, and persists them locally. The suggested `deep-blue-pink` + Glass default is not confirmed.
- The design supports responsive layouts, keyboard use, visible focus, reduced motion, WCAG AA contrast (4.5:1 normal text / 3:1 large text), non-color-only status, and an opaque fallback if blur is unavailable. Review all six theme/material combinations and visual-effects performance on the CPU/8 GiB target; do not silently force baseline users into Solid.
- Full spoken conversations with voiced responses. The default wake phrase is the selected character's name: Jarvis, Rick, or Sebastian; the user can change it. After activation, conversation continues without repeating the wake phrase. Once the assistant has answered, it waits 30 seconds for the user's next reply by default; the user can configure this wait. The wait does not limit active user speech, inference, or speech output. «Хватит» or “Stop” ends the dialogue and returns to wake listening unless the microphone is muted, access is invalid, or required local resources are unavailable. The user can interrupt speech output by speaking a new utterance. When the main window is closed, the assistant continues waiting in the background for its wake phrase. Window close therefore differs from explicitly quitting the assistant. A tray icon and configurable autostart are required; explicit Full Exit stops the assistant and microphone capture.
- Provide an instant microphone-mute button that stops microphone capture for both wake detection and active conversation. A manual mute lasts for the current application session. On a genuine application or Windows restart, resume wake listening if Windows permits it and entitlement/resources are valid; never capture audio when access has expired or the OS denies microphone access. Reopening the main window while the host remains active is not an application restart. Full Exit stops workers and capture until the next authorized launch. Respect OS/hardware mute. Show current state in the main window and tray; exact labels and implementation remain proposed.
- General conversation, internet information search, and weather lookup.
- Multiple selectable personalities using the exact named characters and recognizable voices requested by the owner; original substitute characters are not the target. References include JARVIS, Rick Sanchez, and Sebastian from *Black Butler* (the Sebastian identification is inferred from the owner's series reference; the precise voice actor and language version are unconfirmed). The supplied MP3 remains local. Commercial usage permissions have not been verified. The anime reference is [Black Butler (2008)](https://rutube.ru/plst/510981/); [WIPO copyright material](https://www.wipo.int/documents/d/copyright/docs-en-wo_inf_108.pdf) is background for a later rights review, not a legal conclusion.
- Proactive behavior is configurable: morning plans, daytime reminders, and evening reviews can be enabled or disabled. Triggers include the first entry each day, an approaching meeting, a missed habit, and returning after an absence. Offer initiative settings during first launch. Until the user chooses, proactive speech remains off; skipping the offer is not consent. Ask for a quiet-hours schedule in local time or an explicit choice of no quiet hours; do not assume a default schedule. Quiet hours, call/game suppression, and manual quiet mode suppress proactive voice and use ordinary OS notifications when permitted. They do not mute the microphone or change user-requested conversation behavior. Call/game detection uses system heuristics, a user-selected application list, and manual quiet mode; it cannot guarantee detection of every call or game. When return-after-absence is enabled, the default trigger is 30 minutes without keyboard/mouse input in the interactive session, configurable by the user. This is not proof of physical absence or global OS input monitoring, and does not enable the trigger automatically.
- After sleep or restart, provide one aggregated summary of missed reminders, not a replay of every missed reminder. Catch-up is available only with valid access and OS notification permission. Speak the summary only when proactive-speech settings, quiet hours, calls/games, and the current context permit; otherwise use an ordinary notification. Exclude obsolete, cancelled, or completed targets. Maximum frequency and exact delivery mechanics remain to be designed.
- Quiet hours, active calls, games, and manual quiet mode suppress proactive speech; show ordinary OS notifications when permitted. Exact detection behavior, timing/cooldowns, and notification details remain to be designed.
- The user chooses the time and/or situation for spoken updates, including the listed triggers.

### Connections and capabilities

A settings area called "Connections and capabilities" lets users connect services and grant permissions for calendar, mail, notes, files, program launching, and device control as needed.

Initial integrations include Google Calendar, Outlook, and Gmail. Google Calendar and Outlook synchronize bidirectionally: local changes propagate to the service and remote changes propagate back. The product's own calendar, notes, and projects work independently; Google Calendar synchronization is optional. If the same event is changed on both sides, ask the user which version to keep; never silently choose the most recent write. Permission boundaries and action history require design. By default, the assistant proposes task changes for confirmation. If an application user explicitly asks to skip confirmations, separate revocable permissions may cover task creation, editing, moving, completion, and deletion. Clarify ambiguous targets regardless of these permissions. Permission to delete a task never authorizes deleting a user file. Sending email, deleting files, and overwriting files always require confirmation; task permissions never bypass these confirmations. Habit goal/load changes always require the user's acceptance. Confirmation rules for device control remain to be designed.

### Personalization and memory

The assistant remembers the user's name or nickname. The user can enter a city manually or optionally enable automatic city detection with permission; a city is sufficient for weather, and precise GPS location is not required. Conversation history is stored locally with a 30-day default retention; users can change the period, disable history, or delete all history. This does not approve additional persistent memories by default. Timezone behavior and any future cloud processing remain undecided.

Automatic local backups are required daily and before data-structure or migration updates. Keep seven days of backups by default; the schedule and retention are configurable. Use a separate, configurable local application backup folder outside the working PostgreSQL database; its exact path is unselected. Include conversation history in automatic backups. When history is deleted, show affected backups and offer user-confirmed recreation or deletion; do not silently purge all user files. Exact archive handling, restore behavior, and automatic history-expiry interaction remain open. Do not claim full history erasure before affected-archive handling completes, promise secure physical erasure, or control external copies.

### Commercial model and localization

- Subscription-based product.
- English and Russian application languages.
- Intended audience is not restricted to one region; actual distribution, payment, and service availability require validation later.
- The current release uses local AI only; cloud inference is not allowed. When the trial or subscription is valid and required local resources are available, all local sections, reminders, voice, and conversation work without internet. Search, live weather, and external providers require a network connection. A locally queued intention does not mean a remote operation executed; it does not authorize an automatic retry of an uncertain email send or imply a Djarvis server. The owner authorized downloading and evaluating a local model separately from application programming. API-key support is a separate future capability excluded from the current local-only release. The earlier requirement for a BYOK subscription at 50% of the standard subscription price is retained as a future pricing requirement for that capability. Current subscription amounts and plan structure have not been selected. The full-product trial lasts seven days per device, starting on first use of any function. After trial or subscription expiry, planner and assistant functions are locked, data is retained, renewal/import, data deletion and automatic backups remain available, and microphone capture/proactive speech stop.
