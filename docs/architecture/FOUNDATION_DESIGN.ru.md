# Предложение по основе архитектуры — CP01–CP07

[English version](FOUNDATION_DESIGN.md) · [Требования продукта](../PRODUCT.ru.md) · [Ядро планировщика](PLANNER_CORE.ru.md) · [План компонентов](COMPONENT_PLAN.ru.md)

Дата: 2026-11-03. Статус: подробное техническое предложение для рассмотрения. Узкие решения ADR-001–ADR-008 утверждены; полная архитектура, протокол, схема, алгоритм и поведение компонентов ниже — нет. Документ не утверждает, что что-либо реализовано, создана схема базы, собран пакет или достигнута производительность.

Здесь CP01–CP07 раскрыты как согласованная основа для дальнейшего проектирования. «Рекомендация» означает предложение для рассмотрения. «Решение владельца» обозначает поведение продукта, которое нельзя считать принятым до ответа владельца. Приведённые имена API и полей иллюстративны и могут измениться.

## 1. Область и границы

CP01 определяет владельца процессов и локальное взаимодействие. CP02 — команды, запросы, результаты, разрешения и фиксацию изменений. CP03 описывает логическую модель PostgreSQL и целостность без SQL DDL. CP04 — жизненный цикл и миграции утверждённого частного локального PostgreSQL. CP05 предлагает детерминированное построение плана дня. CP06 задаёт семантику времени, повторений и привычек. CP07 охватывает проекты, заметки, теги, вложения и локальный поиск.

Здесь учитывается утверждённая основа:

- Для UI выбран Flutter; для ядра планировщика и фоновой логики — Python со средой выполнения под управлением приложения.
- Частный изолированный PostgreSQL под управлением приложения работает на компьютере пользователя с Windows. Данные пользователя остаются локально; удалённый бэкенд приложения или облачная база пользовательских данных не выбраны.
- Выбраны локальный профиль и импорт подписанной лицензии с автономной проверкой. Пробный период и истечение доступа определены ADR-005. Обработка ключа резервных копий и политика полного восстановления определены ADR-006.
- При действующем доступе и наличии нужных локальных ресурсов планировщик, напоминания, голос и диалог рассчитаны на работу без интернета. Для поиска в интернете, актуальной погоды и внешних поставщиков нужна сеть.
- Правила продукта о приоритетах, запросе времени крайнего срока, маркере начала, повторах, привычках, завершении задачи, разрешениях, согласии на разделение, допустимости просроченных задач, явной отметке воздержания, выборе для родителя/подзадач и отсутствии автоматических перерывов ограничивают это предложение.

## 2. CP01 — модель процессов и локальный протокол

### 2.1 Варианты и рекомендация

| Вариант | Преимущества | Затраты и риски |
| --- | --- | --- |
| Версионируемый HTTP API запрос/ответ, привязанный к loopback, плюс события WebSocket | Чёткая типизированная граница; запросы легко исследовать; после переподключения можно запросить снимок; общий тип клиента для будущего Android | Нужно слушать только loopback, аутентифицировать клиентов, защищать порт/токен и проверять источники; для потока событий нужны правила переподключения |
| Именованные каналы Windows с ограниченным дескриптором безопасности | Локальный IPC с ACL Windows; не нужен слушающий TCP-порт | Нужна проработка нативного транспорта и взаимодействия Flutter/Python; необходимо определить область пакета/сеанса и повторное подключение; Android потребует другого адаптера |

Рекомендация: один пользовательский Python-хост владеет версионируемым локальным API. HTTP используется для команд и запросов; WebSocket — только для временных уведомлений, после которых клиент перечитывает данные. Слушатель привязывается только к loopback. Создаётся токен доступа на время запуска, передаваемый по защищённому локальному каналу; его нельзя помещать в URL или журналы. Клиенты вне loopback или без аутентификации отклоняются. Это проектная рекомендация, а не гарантия безопасности от другого процесса того же пользователя Windows.

Именованный канал остаётся технически приемлемой альтернативой, если прототип покажет надёжный клиент Flutter/Python и владелец предпочтет его. Windows позволяет задать дескриптор безопасности именованного канала; его стандартный дескриптор может предоставлять более широкий доступ на чтение, поэтому нужен явный ACL. [Безопасность именованных каналов Microsoft](https://learn.microsoft.com/en-us/windows/win32/ipc/named-pipe-security-and-access-rights). HTTP — протокол запрос/ответ без состояния, а WebSocket — отдельный двунаправленный канал с кадрами; поэтому правила переподключения должны входить в контракт приложения. [RFC 9110](https://www.rfc-editor.org/rfc/rfc9110.html), [RFC 6455](https://www.rfc-editor.org/rfc/rfc6455.html).

### 2.2 Владение и границы процессов

Предлагаемые обязанности:

- **Процесс UI Flutter:** экраны, ввод, доступность, отображение локального состояния, вопросы/подтверждения и показ полученных моделей чтения. У UI нет реквизитов базы, и он не принимает решения о бизнес-изменениях локально.
- **Python-хост:** единственный владелец доменных команд, разрешений, планирования, локальных транзакций, состояния планировщика и жизненного цикла рабочих процессов/базы. Он предоставляет версионируемый локальный протокол.
- **Частный процесс PostgreSQL:** только долговременные записи приложения. Хост запускает, контролирует и останавливает только собственный изолированный кластер; перед управлением обязан определить его идентичность.
- **Рабочие процессы моделей/речи:** изолированные временные процессы вычислений. Возвращают кандидаты текста/аудио или структурированный результат инференса; напрямую изменять доменные таблицы или выдавать разрешения им нельзя.
- **Адаптеры внешних служб:** вызываются хостом только после проверки возможностей/разрешений. Результат поставщика хранится отдельно от локального намерения в очереди.

Рекомендуемый порядок запуска: получить блокировку/запись владения хостом в пользовательском сеансе; проверить доступ и пути данных приложения; запустить или подключиться только к идентифицированному экземпляру PostgreSQL приложения; проверить версию схемы и готовность; по требованию инициализировать рабочие процессы; затем открыть локальный протокол UI. Захват звука начинается лишь после проверки доступа, локальных голосовых ресурсов и разрешения микрофона ОС. Отказ ОС в разрешении микрофона отключает захват и зависящие от него голосовые функции, но сам по себе не блокирует ручное использование планировщика или текстовое взаимодействие при действующем доступе. Это соответствует ограничениям продукта и требует дальнейшего проектирования жизненного цикла; функция не реализована.

Закрытие главного окна не останавливает хост или ожидание ключевой фразы. «Полностью выйти» запрашивает штатную отмену, прекращает захват микрофона, останавливает временные рабочие процессы, завершает безопасные локальные операции и затем останавливает только принадлежащий приложению экземпляр базы. Сон, выключение, потеря питания, отказ ОС или истечение доступа могут прервать работу; нельзя обещать доставку в фоне, когда хост или ОС недоступны.

### 2.3 Пример конверта протокола

Все конверты ниже — примеры, а не сгенерированный код или утверждённые имена полей. Даты и моменты времени нужно сериализовать явно; нельзя передавать неуточнённую локальную строку времени и позднее угадывать часовой пояс.

```json
{
  "protocol_version": 1,
  "request_id": "client-generated-id",
  "action_id": "stable-id-for-retry",
  "profile_id": "local-profile-id",
  "command": "CreateTask",
  "expected_revisions": [{"entity_id": "...", "revision": 4}],
  "reference": {"instant": "...Z", "timezone": "Area/City"},
  "payload": {"title": "...", "priority": "high"},
  "approval_id": null
}
```

Ответ должен отличать применённое локальное изменение от ожидающего внешнего эффекта:

```json
{
  "request_id": "...",
  "action_id": "...",
  "state": "AppliedLocal",
  "committed_revision": 5,
  "read_model": {},
  "questions": [],
  "external_effects": []
}
```

Предлагаемые состояния результата: `AppliedLocal`, `QueuedExternal`, `NeedsClarification`, `NeedsConfirmation`, `NeedsInput`, `Conflict`, `Denied`, `Unavailable` и `Failed`. Результат содержит стабильный ID действия и необходимые ревизии. `QueuedExternal` означает только сохранённое намерение. При переподключении UI запрашивает актуальный снимок; пропущенное событие WebSocket не означает потерю команды, а событие нельзя повторять как команду.

### 2.4 События и переподключение

События — подсказки с изменившейся ревизией модели чтения и ID затронутых записей, а не сами авторитетные записи. Их можно объединять. После переподключения или разрыва в ревизиях клиент запрашивает свежий снимок. Хост сохраняет команду до сообщения об успехе. Если хост завершился после записи изменений, но до ответа, повтор с тем же ID действия возвращает сохранённый результат; другой ID означает новое намерение.

Долгий инференс и запросы к поставщикам выполняются вне транзакций базы. Отмена прекращает ожидание ответа или запрашивает отмену рабочего процесса, но не отменяет уже зафиксированную команду. Нужно явно сообщать о переходах состояния, не выдавая преждевременное «готово».

## 3. CP02 — контракты команд, запросов, политик и фиксации

### 3.1 Жизненный цикл команды

Рекомендуемый путь:

1. Разобрать аутентифицированный версионируемый запрос и проверить обязательные поля.
2. Определить цель пользователя. Если остаётся больше одного возможного объекта, вернуть `NeedsClarification`, даже при отключённом подтверждении изменений задач.
3. Загрузить актуальные записи и ожидаемые ревизии; отклонить устаревшую цель или разрешение.
4. Проверить доступ, выданные возможности и политику подтверждений для конкретной операции и текущих данных.
5. Если данных не хватает, вернуть `NeedsInput`; не придумывать приоритет, длительность, дату, получателя или цель.
6. Проверить доменные инварианты и снимок планирования. Если изменения ещё не приняты, вернуть предложение для рассмотрения.
7. В одной короткой транзакции PostgreSQL записать связанные доменные данные, результат для идемпотентности действия, минимальные метаданные аудита и требуемую запись исходящей очереди.
8. Опубликовать новую ревизию только после фиксации. Успех или отказ внешнего поставщика — отдельное последующее состояние.

Вывод классификатора/модели не является полномочием. Он может предложить типизированную команду, но не обходит разрешение, проверку цели, валидацию и обязательное подтверждение.

### 3.2 Примеры типов команд и результатов

| Группа команд | Пример содержимого запроса | Граница успеха |
| --- | --- | --- |
| Задача | название, явно выбранный приоритет, необязательные поля, ожидаемые ревизии | Зафиксирована локальная задача/вхождение и размещение, если оно есть |
| Привычка | ID привычки, наблюдение/измерение, локальный период | Зафиксирована запись; успех не выводится из молчания |
| План | дата/часовой пояс, снимок ревизии, предложенные размещения | Размещения фиксируются только после принятия и повторной проверки |
| Файл | выбранные источник и назначение, точная операция | Удаление/перезапись — только после подтверждения; результат исполнения сообщается позже |
| Почта | получатели, текст, вложения, контекст разрешений | Отправка всегда требует подтверждения; «отправлено поставщику» только после подтверждения поставщика |
| Синхронизация календаря | локальный/внешний ID, ревизия поставщика, курсор | Локальный конфликт или очередь не означают подтверждения от поставщика |

Результат применённой команды должен содержать `action_id`, ревизии зафиксированных записей и краткий код результата. Ответ с уточнением несёт ID кандидатов и безопасные для показа факты. Подтверждение привязывается к точным получателям/тексту/вложениям либо ID задач/изменениям/ревизиям; изменение существенного поля требует нового запроса подтверждения.

### 3.3 Идемпотентность и конкурентность

Использовать ID действия, созданный клиентом и ограниченный профилем и источником команды. Уникальный ключ обработанного действия и его окончательный локальный результат записываются в одной транзакции с изменениями. Повторное использование ID действия с другим нормализованным телом запроса — конфликт, а не вторая мутация. Внешние эффекты получают собственный стабильный ключ и машину состояний; идемпотентность команды сама по себе не обеспечивает однократность операции поставщика.

При принятии плана сравнить снимок ревизий и повторно проверить все влияющие на план записи внутри транзакции принятия. Предлагаемый способ — короткая строка/защита состояния планирования профиля, изменяемая всеми командами задач, календаря, доступности, повторов и значимых привычек. Изменение несвязанной заметки эту ревизию не увеличивает. Это рекомендация по сериализации на уровне приложения, а не требование к PostgreSQL как к базе с единственным писателем. Точные блокировки/изоляция ещё рассматриваются.

### 3.4 Политики и разрешения

Различать четыре понятия: намерение пользователя, разрешённая возможность, необязательное предпочтение не спрашивать подтверждение и обязательное подтверждение. Сохранённое разрешение без подтверждений ограничено выбранными операциями задач, может быть отозвано и проверяется ещё раз при исполнении. Оно никогда не даёт право удалять/перезаписывать файлы, отправлять почту, менять цели привычек или выполнять действия питания/выхода Windows. Неоднозначность всегда требует уточнения. Отправка почты, удаление/перезапись пользовательских файлов и подтверждённые действия выключения/перезагрузки/выхода Windows каждый раз требуют точного подтверждения. Изменения целей/нагрузки привычек остаются предложениями до отдельного принятия.

Разрешение интеграции может быть отозвано, пока элемент ожидает в очереди. Перед отправкой заново проверить разрешение и тело операции. Содержимое веб-страницы/письма, ответ модели и метка источника не могут выдавать разрешения.

## 4. CP03 — логическая модель данных PostgreSQL

Это только концептуальная реляционная модель. Здесь намеренно не выбираются окончательный SQL, версия PostgreSQL, драйвер, представление перечислений, система миграций или пул соединений.

### 4.1 Группы сущностей

| Группа | Предлагаемые записи и связи |
| --- | --- |
| Профиль/настройки | Один локальный профиль; часовой пояс, язык, доступность и выбранные правила — явные записи с ревизиями |
| Задачи | `Task` как шаблон/идентичность; `TaskOccurrence` как выполняемое вхождение; ноль или больше сегментов `SchedulePlacement`; отдельные срок, действие завершения и отметки прогресса частей |
| Повторы | `RecurrenceRule` с исходной локальной точкой отсчёта, периодичностью, именованным поясом, правилом отсутствующей даты месяца и версией; `RecurrenceException` для пропущенных/перемещённых/отменённых исходных вхождений |
| Привычки | `Habit`, версионные расписания `HabitSchedule` с датой действия, паузы, `HabitPeriod`, датированные измерения/отметки |
| Календарь | Внутреннее `CalendarEvent`, идентичность повторения, выбранное внешнее сопоставление, ревизия поставщика, курсор синхронизации и снимки конфликтов |
| Планирование | `DayPlanProposal`, зафиксированная ревизия планирования, элементы предложения и ревизия принятого результата |
| Проекты/контент | `Project`, `Note`, теги и явные таблицы связей; метаданные вложений ссылаются на файлы хранилища приложения |
| Действия | Обработанное действие/результат, разрешения, запросы подтверждения, аудит, внешняя очередь, правила/доставки напоминаний |

Идентичность вхождения не должна быть названием задачи или текущим временем размещения. Перемещение размещения сохраняет исходный ключ повторения. Завершённое вхождение остаётся в истории; завершение одного экземпляра не завершает остальные. Маркер времени начала отличается от занятого `SchedulePlacement`, так как у него не проверено время окончания.

### 4.2 Правила целостности и обоснование

Предлагаемые ограничения базы должны, где возможно, обеспечивать:

- Каждый дочерний объект связан с существующим профилем/родителем; внешние ключи обеспечивают целостность владельца и связей.
- Для задачи указаны обязательное название и явно выбранный приоритет; неявного обычного приоритета нет.
- Длительность сохранённых размещений положительна; конец интервала не включается, поэтому соседние блоки могут соприкасаться. Маркер без длительности не является занятым интервалом.
- У вхождения повторения есть уникальный исходный ключ внутри версии правила; исключения не создают то же вхождение снова.
- У измерения привычки есть стабильный ключ действия/источника для безопасного повтора команды. Разные подлинные измерения количества/длительности за день могут храниться отдельно, а гибкая частота считает одну успешную локальную дату только один раз.
- Один ID действия обрабатывается один раз на профиль; внешний ключ операции уникален в области адаптера/аккаунта.
- Запись завершения задачи отделена от отметок сегментов. Отметки всех сегментов не завершают задачу автоматически; отдельное завершение разрешено и без всех отметок.
- Внешнее сопоставление хранит ID поставщика/аккаунта/календаря/объекта отдельно от локального ID и содержит базовую синхронизированную версию для разрешения конфликтов.

Внешние ключи защищают связи; уникальные ограничения — устойчивые идентичности; проверки — значения одной строки. Проверка пересечения разных временных строк и политик должна оставаться доменной/транзакционной логикой, если позднее не будет выбрано точно ограниченное исключающее ограничение PostgreSQL. Не дублировать производные флаги «просрочено», если их можно вычислить по сроку, времени и состоянию завершения.

### 4.3 План индексов и обоснование

Индексы — предложения для проверки по реальным запросам и представительным данным, а не обещание производительности:

- Уникальные идентификаторы и ключи вхождений: стабильный поиск и предотвращение дублирования повторов.
- `(profile_id, state, deadline_date)` и `(profile_id, scheduled_local_date, state)`: фильтрация списка задач/дня; точные поля зависят от выбранного представления даты.
- `(profile_id, target_id, start_instant)` для размещений и `(profile_id, habit_id, local_period_key)` для записей: сборка дня и вычисление периодов.
- Уникальность внешнего сопоставления по `(provider, account_id, calendar_id, provider_object_id)` и поиск курсора синхронизации по выбранному аккаунту/календарю.
- Очередь внешних действий по `(state, next_attempt_at)` и очередь напоминаний по `(state, due_at)`: возобновление только наступивших работ после перезапуска.
- Связи тегов по `(tag_id, resource_id)` и `(resource_id, tag_id)` — только если нужны запросы в обоих направлениях.
- Индексы поиска по утверждённым локальным текстовым полям, с настройкой языка и отдельной проверкой разрешений перед выдачей результатов. Полнотекстовый поиск PostgreSQL использует нормализованные векторы/запросы и может ускоряться GIN-индексом; это не гарантирует качества русской/английской морфологии, ранжирования или расхода памяти. [Полнотекстовый поиск PostgreSQL](https://www.postgresql.org/docs/current/textsearch-intro.html), [индексы поиска](https://www.postgresql.org/docs/current/textsearch-indexes.html).

Не индексировать все поля на всякий случай: каждый индекс занимает место и увеличивает стоимость записи. Для каждого индекса нужно указать конкретный запрос; пути доступа должны включать фильтрацию по профилю.

PostgreSQL документирует первичные, внешние, уникальные, проверочные и исключающие ограничения и транзакционное поведение. Фактические ограничения выбираются после утверждения модели предметной области. [Ограничения PostgreSQL](https://www.postgresql.org/docs/current/ddl-constraints.html), [ограничения CREATE TABLE](https://www.postgresql.org/docs/current/sql-createtable.html), [транзакции](https://www.postgresql.org/docs/current/tutorial-transactions.html).

## 5. CP04 — жизненный цикл частного PostgreSQL и миграции

### 5.1 Владение экземпляром

Экземпляр PostgreSQL под управлением приложения частный для этого продукта и текущего пользователя. Не смешивать неизменяемые файлы среды выполнения с постоянным каталогом данных, журналами, хранилищем вложений, архивами копий и удаляемым кэшем моделей. Постоянные данные пользователя размещать в каталоге данных приложения, не среди установочных файлов или исходников. Точные пути, архитектура Windows, дистрибутив/версия PostgreSQL, порт, роль/аутентификация и настройки ресурсов не выбраны.

Перед запуском получить блокировку владения пользовательским хостом. Прочитать манифест экземпляра приложения, проверить канонический путь данных, идентичность кластера и ожидаемую основную версию, убедиться, что конечная точка принадлежит этому кластеру. Нельзя присваивать, инициализировать, мигрировать, останавливать или удалять произвольную локальную службу PostgreSQL. Не переключаться на публичную/удалённую базу.

Рекомендуются только loopback-конечная точка, отдельная роль приложения с минимальными полномочиями, защита реквизитов вне обычных журналов и случайный свободный порт, записанный в состоянии приложения. Одного `localhost` недостаточно для аутентификации клиента. Окончательный транспорт/аутентификация требуют платформенной проверки.

### 5.2 Машина состояний жизненного цикла

Предлагаемые состояния: `Absent`, `Initializing`, `Starting`, `WaitingForReady`, `Migrating`, `Ready`, `Stopping`, `Stopped`, `RecoveryRequired`, `IncompatibleVersion`.

| Переход | Проверки и действие | Результат ошибки |
| --- | --- | --- |
| Первый запуск → инициализация | Проверить место, цель приложения, подпись/версию бинарных файлов и пустоту каталога | Показать устранимую ошибку; не инициализировать неоднозначный/непустой каталог |
| Остановлен → запуск | Проверить манифест и блокировку владения; запустить только свой экземпляр | Сохранить данные и сообщить об ошибке старта |
| Запуск → готов | Ограниченно повторять проверку ожидаемого кластера/базы/роли/версии схемы | Прекратить повторы; отметить недоступность или необходимость восстановления |
| Готов → миграция | Создать требуемую восстанавливаемую копию; закрыть новые записи; применить одну версионированную миграцию, по возможности транзакционно | Сохранить исходную копию; при частичном небезопасном откате потребовать восстановления |
| Готов → остановка | Прекратить новые команды; завершить/прервать безопасную работу; закрыть клиентов; остановить только свой экземпляр | Сообщить о незавершённой остановке; данные не удалять |
| Любое → несовместимая версия | Сравнить манифест с поддерживаемой версией бинарных файлов/схемы | Не выполнять разрушительный откат; направить на восстановление или проверенное обновление |

Утилиты управления PostgreSQL следует применять лишь как контролируемые операции экземпляра приложения; после выбора версии нужно описать аргументы запуска, права, готовность, коды завершения, журналы и восстановление. Способ создания установщика и политика службы Windows здесь не выбраны. [PostgreSQL pg_ctl](https://www.postgresql.org/docs/current/app-pg-ctl.html).

### 5.3 Контракт миграции

Каждая миграция имеет стабильный ID, версии схемы до/после, предусловия, требования к транзакции, преобразование данных, постусловия и инструкцию восстановления. Хост проверяет место и идентичность кластера, создаёт обязательную копию до миграции, блокирует новые доменные записи, применяет миграцию, проверяет критические ограничения/модели чтения и публикует новую версию схемы. При падении процесса запуск обнаруживает незавершённую миграцию и идёт по явно заданному пути возобновления/восстановления; нельзя угадывать только по версии бинарных файлов.

Миграции вперёд безопаснее, чем предположение, что старый бинарный файл сможет работать с новой схемой. Откат требует отдельного обратного преобразования или восстановления. Крупное обновление PostgreSQL — отдельная операция, не миграция схемы приложения.

### 5.4 Сбой и восстановление базы

Если PostgreSQL недоступен, запросы, которым он нужен, возвращают `Unavailable`; команды изменения планера не сообщают об успехе. Нельзя молча вести вторую изменяемую копию в памяти или переключаться на файловый запасной вариант. Повторяемые запросы сохраняются только если их статус можно восстановить безопасно. Предоставлять локальные шаги диагностики/восстановления, не раскрывая реквизиты и не объявляя данные потерянными до выяснения.

Любые копирование/восстановление соблюдают ADR-006: ключ под защитой Windows, полный снимок после предпросмотра и свежая копия текущих данных, без восстановления лицензии/доступа, OAuth-реквизитов или образа Windows, соблюдение правил истории. CP15 подробно проектирует копии. `pg_dump` создаёт согласованный снимок одной базы PostgreSQL, однако вложения и метаданные приложения требуют согласования. [pg_dump](https://www.postgresql.org/docs/current/app-pgdump.html), [форматы копий](https://www.postgresql.org/docs/current/backup-file.html).

## 6. CP05 — детерминированное построение плана дня

### 6.1 Входы и инварианты

Планировщик — детерминированный доменный сервис, принимающий снимок входов. Загруженная языковая модель ему не нужна. Модель может распознать намерение или объяснить ответ, но не подставляет длительность, не меняет даты, не придумывает доступность и не фиксирует план.

Снимок включает: дату планирования и именованный часовой пояс; настроенную доступность пользователя; принятые блоки и внешние занятые интервалы с нормализованными началом/концом/признаком свободного времени; ручные закреплённые размещения; доступные открытые вхождения и сроки задач; оценки длительности; потребности по расписанию привычек; перерывы только после задания длительности и частоты; согласие на разделение и принятые ограничения сегментов; актуальные настройки и ревизию входов.

Если длительность задачи неизвестна, до автопланирования вернуть для неё `NeedsInput`. Задача может храниться без неё и, при ручном вводе, иметь маркер начала, но этот маркер не резервирует интервал. Если у встречи/занятого события неизвестен конец или неоднозначен смысл события на весь день/свободного времени, нельзя считать этот промежуток заведомо свободным; нужно вернуть запрос/причину конфликта или исключить часть времени до нормализации.

Жёсткие ограничения: ручное размещение закреплено, пока пользователь явно не разрешит его менять; встречи и недоступные периоды планировщик не переносит; не расширяет доступные часы и не изменяет срок задачи; для задачи только с датой окно размещения — 06:00–22:00 с учётом её собственной длительности, а не 16-часовая задача или общий рабочий день. Просроченная задача остаётся кандидатом автоматического предложения; исходный срок и признак просрочки сохраняются, а применение требует действующего подтверждения/разрешения.

### 6.2 Предлагаемый алгоритм

1. Проверить выбранную дату/пояс и ревизию. Прочитать записи планирования одним согласованным локальным снимком.
2. Разрешить недостающие входы. Запросить длительность, уточнить цель или неоднозначное значение занятого/свободного времени, а не пропускать запись и не придумывать данные.
3. Построить свободные интервалы как настроенную доступность минус встречи, недоступность, ручные блоки и принятые размещения. Конец интервала не включается, поэтому соседние задачи могут соприкасаться.
4. Добавить автоматические перерывы, только если пользователь настроил и длительность, и частоту. Иначе не добавлять их.
5. Собрать кандидатов: доступные открытые задачи и нужные привычки, не превращая пропуски привычек в долг задач. Сохранять отдельность каждого вхождения повтора.
6. Ранжировать кандидатов по принятой политике: задачи с крайним сроком — от ближайшего срока, при равенстве учитывается более высокий приоритет; задачи без срока сортируются по приоритету. Не использовать скрытые веса или расчёт свободного резерва.
7. Для каждого кандидата найти допустимый интервал, вмещающий известную длительность. Техническое предложение использует стабильный порядок выбора времени; выбранный блок и причина показываются в предварительном просмотре. Нельзя утверждать глобальную оптимальность жадного алгоритма.
8. Разделять только задачу с явным согласием. Не придумывать границы или минимальную длительность сегментов. Пока настройки не утверждены, запросить их или вернуть причину неразмещённой задачи. Отметка сегмента — только прогресс; вхождение завершается отдельной явной командой.
9. Вернуть добавления, переносы, неизменённые закреплённые блоки, неразмещённые задачи, выполнимость сроков и ревизии входов. Пока ничего не записывать.
10. После принятия заново проверить ревизии и все ограничения в короткой транзакции. Если вход изменился, вернуть `Conflict` и запросить новое рассмотрение. Иначе атомарно записать размещения и результат действия.

### 6.3 Правило ранжирования и выбор владельца

Принятая политика продукта: сперва срок, затем приоритет; задачи без срока сортируются по приоритету. Не использовать скрытую взвешенную формулу приоритета/срока или неутверждённый расчёт свободного резерва. Предлагаемый детерминированный порядок при одинаковых сроке/приоритете: исходная дата расписания, затем стабильный ключ вхождения. Для задач без срока — приоритет и стабильный ключ вхождения. Эти технические правила ничьей не выбраны владельцем.

План всё равно может оказаться невыполнимым. Сообщить о пропущенном/невыполнимом сроке и причине; не переносить дату, не расширять молча часы работы, не объявлять перегруженный день решённым. Срок задачи и плановое размещение — разные факты.

### 6.4 Завершение разделённой задачи

Принятое поведение: пользователь отдельно включает разделение для задачи; отметки сегментов показывают прогресс, но не завершают задачу; выбранное вхождение завершается отдельным действием, даже если отмечены не все сегменты. Завершение не затрагивает другие или будущие вхождения. Точное имя API не утверждено.

Принятая политика: после явного завершения освободить только оставшиеся будущие блоки выбранного вхождения и сохранить историю; соседние и будущие вхождения не менять. Предлагаемая техническая реализация помечает эти размещения как освобождённые/отменённые и сохраняет их прошлые значения в истории. Граница, когда блок уже начался до момента завершения, но кончается позже, остаётся открытой. Также нужно определить отмену напоминаний по таким блокам.

## 7. CP06 — время, повторения и привычки

### 7.1 Временные значения

Использовать разные логические типы:

- **Календарная дата:** дата планирования без времени либо неполный ввод срока, ожидающий обязательного уточнения времени; она не является сохранённым полным сроком и не превращается автоматически в полночь UTC.
- **Локальные дата/время:** настенное время с явным именованным поясом для повторяющегося личного расписания.
- **Момент времени:** точка глобальной временной шкалы; сохраняется отдельно от именованного пояса будущих повторений.
- **Интервал размещения:** начало и исключительный конец как моменты времени, а также контекст локального пояса; длительность положительна и отделена от срока.
- **Маркер только времени начала:** локальные дата/время без известной длительности; отображается, но не считается занятым интервалом.

PostgreSQL `timestamp with time zone` хранит и нормализует момент, но не исходное имя пояса. Идентификатор пояса и локальную точку отсчёта повторения нужно хранить отдельно. Даты без времени остаются календарными датами, а не приводятся к полуночи UTC. [Типы даты/времени PostgreSQL](https://www.postgresql.org/docs/current/datatype-datetime.html).

Для каждой привычки и личного повтора пользователь выбирает следовать текущему местному времени или сохранить исходный фиксированный пояс. Если выбор не сделан, при смене пояса нужно спросить. Не применять это правило к внешним встречам и не менять исторические записи.

### 7.2 Переход на летнее/зимнее время

Принятая политика продукта: если запрошенное локальное время попало в пропуск при переходе часов, предложить ближайшее допустимое локальное время и запросить подтверждение; если локальное время повторяется, показать оба возможных момента и запросить выбор с подтверждением. Нельзя незаметно сдвигать время или выбирать один из вариантов. Конкретная реализация поясов, детали схемы и способ ожидания уточнения для сгенерированного вхождения остаются техническими вопросами.

Для фактического размещения сохранять намерение пользователя в местном времени и разрешённый момент времени. Если правила пояса меняются, прошлые моменты оставить неизменными, а будущие повторения сформировать заново по выбранному поясу/правилу; показать новые будущие размещения для рассмотрения, не переписывая историю.

### 7.3 Идентичность повтора и долг

У каждого повтора есть версия правила, исходная локальная точка отсчёта, именованный часовой пояс, периодичность, выбранная политика местного/фиксированного пояса и стабильный ключ исходного вхождения. Перенос меняет размещение, но не идентичность вхождения. В RFC 5545 стандарт календарного обмена различает правила повторения, ссылки на часовые пояса и исходный ID экземпляра. [RFC 5545](https://www.rfc-editor.org/rfc/rfc5545).

Интервал вычисляется от исходной точки отсчёта, а не времени выполнения. Пример: задача от 01.11.2026 раз в семь дней выполнена 03.11.2026; следующий срок остаётся 08.11.2026. Пропуски повторений остаются отдельным открытым долгом. Для отсутствующей даты месяца у каждого правила выбирается последний день (по умолчанию) или пропуск. 31 января 2027 → 28 февраля → 31 марта, а не 28 марта.

Генерация повторов идемпотентна: уникальный ключ вхождения не даёт создать его второй раз. Перенесённый/отменённый экземпляр остаётся связанным с исходным ключом, чтобы синхронизация/повторная генерация не создали дубль. Остаются открытыми: какие исторические экземпляры материализовать, область изменения правила (одно, это и последующие, всё правило) и хранение исключений.

### 7.4 Периоды и статистика привычек

Наблюдения-измерения хранятся отдельно от оцениваемых периодов расписания. Приняты четыре типа: да/нет, количество, длительность и воздержание. Запись содержит локальную дату/период, значение/единицу при необходимости и сведения об исправлении. Успех воздержания засчитывается только при явном сообщении пользователя «соблюдено»; отсутствие отметки не является успехом.

Неделя начинается в понедельник по выбранному поясу привычки. Гибкая частота считает разные успешные дни; несколько измерений количества/длительности за день могут учитываться в общем измерении, но в недельную квоту засчитывается не более одного дня. Если после паузы остаётся меньше доступных дней, чем требуется квотой, гибкая неделя считается приостановленной: нет пропуска, разрыва серии или автоматического снижения цели. Фиксированная серия считает подряд успешные запланированные дни; гибкая — успешные недели; пауза замораживает применимую серию. Пропуски привычек остаются статистикой, а не долгом задач.

Исправление разрешено для любой прошедшей даты в течение срока существования привычки, но не до создания привычки и не как будущий фактический успех. Нужно сохранять историю исправлений и пересчитывать результат с целью, действовавшей на дату исправления. Точная запись аудита и механика пересчёта — технические предложения.

Предлагаемый контракт измерений: количественные наблюдения содержат типизированную единицу и число; измерения длительности — прошедшее время с объявленной единицей. В принятом режиме суммирования порции сохраняются отдельно и складываются только в совместимых единицах. В режиме итога дня используется введённый итог, а не сумма прежних итогов. Занятия на длительность складываются за день; приняты таймер с паузой и ручной ввод. Несовместимые единицы не складываются. Успех «да/нет» отмечается явно. Для воздержания только явное сообщение «соблюдено» считается успехом; срыв и отсутствие отметки не являются успехом. Правило принято; точное представление записи остаётся открытым. Решения владельца: набор/преобразование единиц, пороги, смена режима количества и обработка границ измерения времени, представление записи воздержания, причина/авторизация исправления, расчёт показателей при паузах и момент окончательной фиксации пропуска незавершённой гибкой недели. Принятая политика исправлений любой прошедшей даты сохраняется; открыто только её аудиторское представление. Нельзя автоматически создавать компенсирующие задачи или применять новое значение цели без принятия.

## 8. CP07 — проекты, заметки, теги, вложения и поиск

### 8.1 Логические записи

Предлагаются проекты профиля со стабильными ID и ревизиями. Архивация должна скрывать проект из активных представлений, сохраняя связанные задачи, заметки, вложения и историю; удаление должно требовать просмотра последствий и отдельного подтверждения, а точная политика каскадирования/хранения остаётся на рассмотрение владельца. Задача может иметь необязательную ссылку на проект. Заметка имеет стабильный ID, заголовок/текст, версии создания/изменения и необязательную связь с проектом; предлагается обычный текст или ограниченный безопасный формат, без отображения активного HTML/скриптов. Теги — пользовательские метки с нормализованным отображаемым текстом и связями многие-ко-многим с поддерживаемыми типами записей. Точные поля, вложенность, формат заметок и типы объектов для тегов остаются предложениями, не новыми требованиями.

Дополнительные поля задач должны различать значения: чек-лист — только метаданные прогресса, он не завершает задачу; подзадачи — отдельные записи задач со своим статусом и явной связью с родителем. Если у родителя есть незавершённые подзадачи, показать «Закрыть задачу» и «Закончить подзадачи». Выбор «Закончить подзадачи» возвращает к списку подзадач, родитель остаётся незавершённым. «Закрыть задачу» завершает только родителя; подзадачи остаются активными и связанными. Многоуровневая вложенность без фиксированного продуктового ограничения и сворачиваемые ветки приняты (PLAN-014). Политика архива/удаления и наследование проекта/срока/приоритета остаются выбором владельца. По принятому правилу скрытие дополнительных полей сохраняет их значения.

Вложение — метаданные со ссылкой на объект-файл в хранилище приложения и на запись-владельца. База хранит стабильный ID вложения, непрозрачный относительный ключ хранения, исходное отображаемое имя, тип файла при наличии, размер в байтах, хэш, время создания и состояние жизненного цикла. Пользовательский путь нельзя напрямую использовать как ключ хранения; вложение не должно становиться неограниченным исполняемым действием.

### 8.2 Граница файла и транзакции

Файловая система и PostgreSQL не участвуют в одной обычной транзакции. Рекомендуемый процесс добавления:

1. Проверить выбранный пользователем читаемый источник и допустимую запись-цель.
2. Скопировать байты во временную область приложения; применить утверждённые ограничения размера/типа; вычислить хэш и проверить копию.
3. Где это поддерживается, атомарно переименовать временный файл в неизменяемое расположение приложения на том же томе.
4. В короткой транзакции базы добавить метаданные вложения и связь с владельцем.
5. Если запись метаданных не удалась, оставить восстанавливаемую отметку «сирота» либо после безопасной проверки удалить несвязанный временный объект; не показывать битую ссылку.

Сбой может произойти между перемещением файла и фиксацией метаданных. При запуске сверка должна находить несвязанные временные/итоговые файлы, не удаляя объект активной операции. Снимок резервной копии согласует базу со связанными файлами вложений и манифестом. Удаление/перезапись исходного файла пользователя — отдельное действие с обязательным подтверждением; копирование вложения не даёт разрешения менять оригинал.

### 8.3 Поиск и границы приватности

Глобальный поиск сначала обращается к разрешённым локальным записям. Результаты содержат тип/ID и безопасный фрагмент; при открытии заново проверяется доступ и актуальная ревизия. Индексы поиска — производные данные, которые можно перестроить из исходных записей. Не копировать историю разговоров, содержимое писем или текст вложений в постоянный индекс, пока владелец отдельно не включил эти данные и не определил их срок хранения/доступ.

Полнотекстовый поиск PostgreSQL — кандидат для заметок/задач/проектов. Настройки языков для английского и русского следует задавать явно; качество морфологии/ранжирования нельзя обещать без проверки реальных текстов. GIN-индекс — кандидат для часто ищущихся нормализованных полей; окончательный индекс и план запросов требуют представительных данных. [Текстовый поиск PostgreSQL](https://www.postgresql.org/docs/current/textsearch-intro.html), [типы индексов](https://www.postgresql.org/docs/current/textsearch-indexes.html).

Поиск в интернете — отдельная явная возможность помощника, она может отправить запрос пользователя наружу. Это не локальный поиск записей; он требует отдельного разрешения/описания сетевого обмена. Заметки и проекты, не зависящие от погоды, остаются доступны офлайн при действующем доступе.

## 9. Примеры взаимодействия компонентов

### Создание задачи и запрос плана

1. Пользователь задаёт название и явно выбирает приоритет; если приоритета нет, его спрашивают. Остальные поля необязательны, если не нужны запрошенной операции.
2. Задачу можно сохранить без длительности. Позже `BuildDayPlan` возвращает `NeedsInput` для длительности, не придумывая её.
3. Пользователь принимает маркер только времени начала. Он сохраняется как маркер, а не занятый интервал.
4. Планировщик загружает снимок с ревизией, соблюдает ручные блоки и только настроенные перерывы, затем выдаёт предварительный план с причинами неразмещения.
5. Пользователь принимает план; хост проверяет ревизии и атомарно записывает размещения. Если изменились встреча, доступность или задача, возвращается конфликт и строится новое предложение.

### Запись привычки и исправление истории

1. Пользователь записывает измерение на выбранную локальную дату привычки. Тип/единица сверяется с версией расписания, действовавшей тогда.
2. Для гибкой частоты успех учитывается один раз за различную локальную дату, даже если сохранилось несколько измерений.
3. Если дата попала в неделю с паузой или является исправлением задним числом, обновить аудит и пересчитать исторический период с целью, действовавшей тогда.
4. Предложение изменить цель остаётся ожидающим до принятия; разрешение не спрашивать подтверждение для задач не применимо.

### Заметка и файл

1. Создать/обновить текст заметки в локальной транзакции и вернуть её ревизию.
2. Подготовить, проверить и переместить файл, затем зафиксировать метаданные; при сбое записи поставить на безопасную очистку/сверку.
3. Локальный индекс находит текст заметки; при чтении заново проверяется доступ.
4. Копия согласованно включает метаданные и связанные файлы; восстановление выполняется как полное после предпросмотра.

## 11. Будущие критерии приёмки

Это будущие критерии проектирования/реализации, а не тесты, выполненные для этого документа:

- Дубликат ID возвращает исходный результат; другое тело с тем же ID отклоняется.
- Неоднозначная цель требует уточнения даже при разрешении не спрашивать подтверждение задачи; почта/файлы/действия питания требуют подтверждения.
- Устаревший план отклоняется после добавления встречи, изменения длительности задачи, доступности или пояса.
- Задачи со сроком сортируются от ближайшего срока, затем по приоритету; задачи без срока — по приоритету; равные входы дают одинаковый результат.
- Ручной маркер начала не занимает слот. До планирования запрашивается длительность.
- Ручные размещения закреплены; разделение и перерывы происходят только при явных настройках.
- Завершение одного разделённого вхождения освобождает только его оставшиеся будущие блоки и сохраняет историю; проверить границу уже начавшегося блока.
- Недельный повтор сохраняет исходную точку и долг; январское 31-е число соответствует выбранному правилу отсутствующей даты.
- Режим местного/фиксированного пояса однозначен после поездки; при DST-разрыве предлагается допустимое время, при повторе — два момента, в обоих случаях нужно подтверждение.
- Несколько записей привычки за день учитываются как одна дата частоты; пауза ниже квоты не образует пропуск/разрыв; исправление пересчитывается с исторической целью.
- Неудачная миграция, падение процесса или заполненный диск при копировании файла оставляют восстанавливаемое состояние без частичных видимых записей.
- Индекс поиска можно перестроить без включения неразрешённых разговоров, почты или текста вложений.
- Локальный планер работает без сети при действующем доступе/ресурсах; внешние поставщики/поиск/погода недоступны без сети и не подразумевают выполнение удалённой команды.

Для этого предложения не выполнялись программирование приложения, создание SQL-схемы/базы, установка пакетов, измерения ресурсов или тестирование.

| FD13 | Неуточнённые детали продукта | Сохранять открытыми конфликты дата/время, размеры/буферы сегментов и поля проектов/заметок | Поведение продукта требует решения владельца; не угадывать значения |
| FD14 | Размещение просроченной задачи | Просроченные задачи остаются кандидатами автоматических предложений; исходный срок и признак просрочки сохраняются; действует существующее подтверждение/разрешение | Политика продукта принята; технические детали остаются открытыми |
| FD15 | Родитель с незавершёнными подзадачами | Показать «Закрыть задачу» (завершается только родитель, дети активны/связаны) или «Закончить подзадачи» (возврат к списку детей, родитель не завершён) | Выбор продукта принят; точная интеракция остаётся предложением |
| FD16 | Успех воздержания | Успехом считается только явная отметка пользователя «соблюдено»; отсутствие отметки не является успехом | Политика продукта принята; хранение/метрики остаются предложениями |

Узкие политики FD05–FD07, FD14–FD16 приняты. Остальные технические предложения требуют рассмотрения; они не разрешают программирование, установку, миграцию, загрузку или замер производительности.

## Принятые измерения и вложенность (PLAN-014)

- Для каждой количественной привычки выбирается режим: складывать отдельные порции (по умолчанию) или вводить общий итог дня. Ввод общего итога не является дополнительной порцией; исправления сохраняются в истории. Переключение режимов и детали единиц/порогов ещё требуют проработки.
- Привычки на длительность поддерживают таймер с паузой и ручной ввод времени. Несколько занятий складываются за день. Поведение таймера при сне, полном выходе, сбое и переходе через полночь остаётся открытым; предлагаемый контракт данных должен предотвращать двойной учёт.
- Подзадачи поддерживают несколько уровней без фиксированного продуктового ограничения глубины; интерфейс позволяет сворачивать ветки. Это не обещание бесконечной ёмкости устройства. Предотвращение циклов и загрузка больших деревьев — технические требования для рассмотрения. Наследование, перенос веток и удаление ещё требуют проработки. Прежнее поведение завершения родителя сохраняется.
