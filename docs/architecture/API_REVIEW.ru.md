# API ядра v1 — обзор утверждённого решения

[English version](API_REVIEW.md) · [полный каталог](API.ru.md) · [утверждённая схема](SCHEMA.ru.md) · [решения](DECISIONS.ru.md) · [модули](MODULES.ru.md)

Статус: обзор утверждённого каталога API, PLAN-037, 2026-11-05. Схема и архив утверждены (ADR-024), API — ADR-025. **Ф0 не разрешена.**

## 1. Граница и форма

Flutter-интерфейс отправляет команды и запросы Python-ядру через локальный HTTP; события приходят по WebSocket. Модель не получает прямой HTTP-доступ: ей доступны только ограниченные типизированные инструменты, которые исполняет то же ядро. Команда несёт идентификатор действия для безопасного повтора, ожидаемые ревизии и контекст времени. Результат явно сообщает: применено локально, поставлено во внешнюю очередь, требуется ввод/уточнение/подтверждение, конфликт, отказ или ошибка.

## 2. Пользовательские потоки

| Поток | Основные команды и запросы | Гарантия |
| --- | --- | --- |
| Дела и подзадачи | `CreateTask`, `EditTask`, `CompleteOccurrence`, `DeleteTask`, `GetTask` | Приоритет обязателен; неоднозначная цель и выбор судьбы подзадач уточняются |
| План дня | `BuildDayPlan`, `EditDayPlanDraft`, `ApplyDayPlan`, `GetDayView` | Черновик редактируется до принятия целиком; ревизии защищают от устаревшего плана |
| Привычки | `RecordHabitEntry`, `CorrectHabitEntry`, `StartTimer`…`StopTimer`, `GetHabitStats` | История исправлений сохраняется; предложения смены цели применяет пользователь |
| Календарь и почта | `CreateEvent`, `SyncNow`, `ResolveSyncConflict`, `SendMail` | Конфликты календаря решает пользователь; отправка письма всегда требует подтверждения |
| Голос и разрешения | `SetMicrophoneMuted`, `StartListening`, `Approve`, `GrantCapability` | Ядро проверяет доступ и точное подтверждение независимо от предложения модели |
| Сохранность данных | `PreviewRestore`, `Restore`, `DeleteHistory` | Предпросмотр и бэкап текущих данных перед восстановлением; прежние права и очереди не возвращаются |

Полный список команд, полей, событий и кодов ошибок находится в [каталоге API](API.ru.md). События служат подсказкой перечитать данные после изменения; пропущенная ревизия приводит к полному обновлению экрана.

## 3. Уточнения после сверки

1. `origin` назначает ядро по вызывающему процессу и внутреннему пути, а не принимает как право из тела запроса. Иначе клиент мог бы заявить источник `sync` или `assistant` и обойти разные правила подтверждения.
2. `approval_id` связан с исходным действием, точным содержимым и ревизиями. Изменение письма или цели требует нового подтверждения; повторное использование подтверждения не запускает другое действие.
3. `ResolveUnknownOutbox` не отправляет письмо повторно без нового точного подтверждения и предупреждения, что первая попытка могла сработать.
4. `Restore` возвращает утверждённый набор пользовательских данных по ADR-023–024; разрешения, подключения и старые очереди не возвращаются.

Эти уточнения утверждены в составе ADR-025 и внесены в API. Они не меняют утверждённую схему, правила проекта или разрешение на программирование.

## 4. Граница решения

Утверждённый каталог закрепляет имена команд/запросов, классы результатов, основные поля, события и правила доступа v1. Детальные JSON-схемы, генерация клиента, реализация, контрактные тесты и проверка на настоящем PostgreSQL появятся после отдельного разрешения программирования. После API следующим отдельным решением будут модули; Ф0 требует собственного явного разрешения.
