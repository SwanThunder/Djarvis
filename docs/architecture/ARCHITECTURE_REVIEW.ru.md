# Архитектура процессов и структура репозитория — пакет для рассмотрения

[English version](ARCHITECTURE_REVIEW.md) · [полный план](IMPLEMENTATION_PLAN.ru.md) · [технические детали](TECHNICAL_DESIGN.ru.md) · [решения](DECISIONS.ru.md) · [отчёт о готовности](READINESS.ru.md)

Статус: предложение для владельца, PLAN-033, 2026-11-05. Фазы Ф0–Ф7 и их критерии уже утверждены (ADR-018); T1–T6 уже утверждены (ADR-015). Сейчас предлагается согласовать только архитектуру §1 и структуру каталогов §2 полного плана. Схема базы, API, модули и разрешение Ф0 остаются отдельными решениями.

## 1. Процессы и владение

| Процесс | Владеет | Запуск и завершение |
| --- | --- | --- |
| Интерфейс Flutter (Djarvis.exe) | Окно, ввод, значок трея, показ состояний; без прямого доступа к базе и секретам | При входе пользователя или вручную; закрытие окна скрывает его в трее, полный выход инициирует остановку всего приложения |
| Python-ядро (djarvis-core.exe) | Команды, права, планировщик, напоминания, звук, подключения; один экземпляр на учётную запись Windows | Интерфейс находит работающий экземпляр или запускает его; ядро управляет дочерними процессами и завершает их при полном выходе |
| Частный PostgreSQL 18 | Локальные данные одной учётной записи Windows | Ядро поднимает и останавливает его; при ошибке готовности показывает восстановимое состояние, не создаёт вторую базу |
| Локальная языковая модель и речевые рабочие | Только вычисления; запись в базу идёт через ядро | Ядро запускает модель по требованию и освобождает при простое; речевые рабочие подчинены аудиосеансу |

При падении окна ядро остаётся отдельным процессом; при повторном запуске интерфейс подключается к нему. Если ядро недоступно, интерфейс проверяет файл подключения и процесс, один раз пытается запустить ядро и ждёт готовности до 15 секунд (TECHNICAL_DESIGN §1.1); затем показывает ошибку с действием «Повторить». Бесконечного автоматического перезапуска нет. При новом запуске ядро проверяет состояние уже существующего кластера PostgreSQL и подключается только к проверенному собственному экземпляру; при неоднозначном владельце или повреждении показывает RecoveryRequired, не создаёт вторую базу. Один владелец процесса и частной базы защищает от конкурирующих запусков. Эти детали восстановления предлагаются на согласование вместе с архитектурой.

## 2. Связь и поток данных

Интерфейс отправляет команды и запросы ядру через HTTP на 127.0.0.1; WebSocket даёт уведомление перечитать изменившиеся данные. Файл подключения в папке пользователя содержит случайный порт, одноразовый токен и ID экземпляра; его защищают права Windows. Ядро проверяет токен, Host, Origin и версию протокола. Контракт определён моделями Pydantic и генерируется для Dart. Команды от экрана и помощника проходят одинаковую проверку прав, ревизий, подтверждений и идемпотентности. Модель не пишет в PostgreSQL напрямую. Внешние поставщики и сетевые сбои не блокируют локальный планер.

## 3. Предлагаемая структура кода

Полный список каталогов находится в [IMPLEMENTATION_PLAN §2](IMPLEMENTATION_PLAN.ru.md#2-структура-репозитория). Главные границы:

- core/djarvis_core: api, contract, app, domain, storage, db, assistant, audio, reminders, integrations, safety, host;
- ui: Flutter приложение, дизайн-система, экраны, клиент контракта и значок трея;
- packaging: установщик, упаковка Python/PostgreSQL и манифест моделей;
- scripts: генерация контракта и сборка; docs и Plan: документация и общий журнал.

Текущий src/ — организационный каркас без кода приложения; data/, cache/, logs/ и tmp/ являются локальными рабочими папками и могут содержать материалы подготовки. После согласования структура core/ + ui/ создаётся в Ф0. Пользовательская база при установке будет в частной папке учётной записи Windows, а не в репозитории. Прежние пустые каталоги не определяют архитектуру будущего кода; удаление или перенос локальных данных сюда не входит.

## 4. Причины и границы согласования

Flutter остаётся единственным владельцем интерфейса и трея. Python-ядро даёт одну точку правил, которой пользуются окно, голос и фоновые задания. PostgreSQL скрыт за ядром; схема и миграции рассматриваются отдельно. Loopback HTTP/WebSocket и генерация типов позволяют сохранить один контракт для интерфейса и будущего клиента, но Android и синхронизация ещё не проектируются как часть этого решения.

Предлагаемая архитектура проверяется в Ф0 запуском встроенного Python и частного PostgreSQL, подключением интерфейса по токену, повторным открытием окна, вторым запуском и полным выходом. В Ф1 проверяются идемпотентность, ревизии, события и восстановление после сбоев. Реальная приёмка на 8 ГиБ — в Ф7. Эти критерии уже утверждены; этот обзор не расширяет фазы.

**Решение сейчас:** принять либо исправить только архитектуру процессов и структуру репозитория из §§1–2 полного плана. После этого по ранее выбранному порядку отдельно рассмотреть схему → API → модули, затем отдельно решить о Ф0.
