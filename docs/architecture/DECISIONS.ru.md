# Реестр решений по архитектуре

[English version](DECISIONS.md)

Утверждены четырнадцать решений с ограниченной областью: ADR-001 выбирает Flutter для интерфейса и необходимого UI-кода на Dart; ADR-002 выбирает PostgreSQL как локальную базу бэкенда; ADR-003 выбирает Python для логики ядра/фонового процесса со своей упакованной средой выполнения; ADR-004 выбирает управляемый приложением изолированный локальный экземпляр PostgreSQL; ADR-005 определяет локальный профиль, импорт офлайн-лицензии и поведение пробного периода/окончания доступа; ADR-006 выбирает защиту ключа резервных копий средствами Windows без отдельного пароля/ключа восстановления и политику полного снимка для восстановления; ADR-007 фиксирует три политики планировщика: порядок приоритетов, неоднозначность DST и оставшиеся размещения сегментированной задачи. ADR-008 фиксирует размещение просроченного, явный успех воздержания и выбор завершения родителя/подзадач. ADR-009 фиксирует режимы измерения привычек и многоуровневые подзадачи. ADR-010 фиксирует лимит устройств лицензии, перенос и поведение при переводе часов назад. ADR-011 заменяет сторонних персонажей своими. ADR-012 выбирает ключ пользователя для поиска и MET Norway для погоды. ADR-013 называет персонажей и задаёт навигацию, подтверждения действий с устройством и папку бэкапов по умолчанию. ADR-014 выбирает движки синтеза речи, поискового провайдера и защиту рабочей базы. Точные версии, драйверы, распространение среды выполнения/базы, зависимости установщика, формат/эмитент лицензии, детали оплаты, схема, криптографическая реализация/ключи и остальная архитектура не утверждены. Существующие папки остаются организационной основой.

## ADR-001 — Flutter для интерфейса и необходимая реализация на Dart

- Дата: 2026-11-03
- Статус: УТВЕРЖДЕНО (ограниченная область действия)
- Контекст: Владелец требует заданный визуальный дизайн Djarvis, сначала Windows 10/11, затем Android. Владелец подтвердил: «Flutter Подходит; теперь подробно ядро планера, данные и взаимодействие».
- Рассмотренные варианты: Flutter/Dart и .NET MAUI/C# сравнивались как варианты UI в первоначальном предложении.
- Решение: Использовать Flutter как платформу интерфейса и Dart только в объёме, необходимом для реализации интерфейса.
- Последствия: Flutter выбран для направления UI; .NET MAUI — ранее рассмотренная альтернатива, а не активный конкурент для UI. Язык ядра/фонового процесса отдельно выбран как Python в ADR-003. Точные версии SDK Flutter и зависимости, границы ядра/фонового процесса, драйвер/схема базы, среды моделей, протоколы процессов, целевые показатели производительности и архитектура в целом остаются нерешёнными. Это решение не разрешает программирование; реализация требует отдельного рассмотренного плана и согласия владельца.
- Основание согласования: Прямое заявление владельца выше, 2026-11-03. [Поддерживаемые платформы Flutter](https://docs.flutter.dev/reference/supported-platforms).

## ADR-002 — PostgreSQL для базы данных бэкенда

- Дата: 2026-11-03
- Статус: УТВЕРЖДЕНО (только выбор базы данных)
- Контекст: Владелец прямо подтвердил: «для бэкенда PostgreSQL» и уточнил, что база работает локально на компьютере пользователя; удалённого бэкенда приложения и облачных пользовательских данных не будет.
- Рассмотренные варианты: Выбран PostgreSQL; прежние предложения по реализации на SQLite заменены и не являются активным выбором базы.
- Решение: Выбрать PostgreSQL как локальную базу бэкенда на устройстве пользователя.
- Последствия: Это не утверждает удалённое/серверное развёртывание, облачные пользовательские данные, бэкенд на Dart или более широкую архитектуру. ADR-004 отдельно утверждает управляемый приложением жизненный цикл изолированной локальной копии; точные бинарные файлы/дистрибутив, версия, драйвер, модель соединений/пула, схема/DDL, миграции, упаковка среды выполнения, зависимости установщика и архитектура в целом остаются нерешёнными. Эти решения не разрешают реализацию.
- Основание согласования: Прямое заявление владельца, 2026-11-03.

## ADR-003 — Python для ядра планировщика и фоновой логики

- Дата: 2026-11-03
- Статус: УТВЕРЖДЕНО (только направление языка/среды выполнения)
- Контекст: Владелец выбрал Python для ядра планировщика и фоновой логики, со своей упакованной средой выполнения. Flutter/Dart остаётся направлением интерфейса по ADR-001.
- Рассмотренные варианты: Python выбран для ядра/фоновой логики; Dart ограничен необходимой реализацией UI на Flutter.
- Решение: Использовать Python для логики ядра планировщика и фонового процесса с отдельной средой выполнения, управляемой приложением.
- Последствия: Не выбраны версия Python, драйвер PostgreSQL (включая psycopg или asyncpg), локальный транспорт/фреймворк, способ заморозки или встроенного распространения, схема/зависимости/детали установщика. Пользовательский сценарий не должен требовать терминал, глобально установленный Python или ручную установку пакетов. Это требование к будущему продукту, не готовая функция. ADR не разрешает программирование.
- Основание согласования: Прямое согласие владельца, 2026-11-03.

## ADR-004 — Управляемый приложением изолированный локальный PostgreSQL

- Дата: 2026-11-03
- Статус: УТВЕРЖДЕНО (только направление жизненного цикла)
- Контекст: Владелец утвердил изолированную частную копию PostgreSQL локально на компьютере пользователя, которой управляет приложение.
- Рассмотренные варианты: Выбран управляемый приложением изолированный локальный экземпляр; удалённый бэкенд и облачные пользовательские данные исключены.
- Решение: Приложение управляет жизненным циклом своей частной локальной копии PostgreSQL, включая запуск и остановку по необходимости.
- Последствия: В планируемом пользовательском сценарии не нужны консоль и ручные операции с базой. Точные бинарные файлы/дистрибутив PostgreSQL, версия, упаковка среды выполнения, драйвер, локальный механизм связи, схема, миграции, зависимости установщика и восстановление остаются предложениями. Это не разрешает устанавливать или реализовывать базу сейчас.
- Основание согласования: Прямое согласие владельца, 2026-11-03.

## ADR-005 — Импорт автономной лицензии и поведение пробного периода/доступа

- Дата: 2026-11-03
- Статус: УТВЕРЖДЕНО (только сценарий доступа и состояния продукта)
- Контекст: Владелец выбрал локальный профиль без обязательного аккаунта, импорт подписанного файла лицензии с офлайн-проверкой и семидневный пробный период, начинающийся при первом использовании любой функции продукта.
- Рассмотренные варианты: Выбран локальный профиль и импорт файла лицензии; требование аккаунта внутри приложения и собственный сервер активации/прав исключены.
- Решение: Покупатель импортирует подписанный файл лицензии, приложение проверяет его автономно. Семидневный пробный период на устройство начинается при первом использовании любой функции продукта, включая ручной планировщик; настройка и ожидание загрузок его не запускают. По окончании пробного периода или подписки функции планировщика и помощника блокируются, пользовательские данные сохраняются. Продление/импорт, удаление данных по инициативе пользователя и автоматические резервные копии остаются доступны; захват микрофона и инициативная речь полностью останавливаются.
- Последствия: Не выбраны формат лицензии, алгоритм подписи, эмитент/инструментарий, платёжный поставщик, цена, механизм продления, детали привязки к устройству или допустимая погрешность часов. Политика защиты ключа и восстановления копий отдельно уточнена в ADR-006, её реализация открыта. Это не утверждает собственный сервер активации и не разрешает реализацию. Потребности в идентификации/аккаунте для будущей облачной синхронизации требуют отдельного проектирования.
- Основание согласования: Прямые выборы владельца F5, F6 и F8, 2026-11-03.

Уточнение PLAN-012: владелец выбрал месячную и годовую подписки; цены и механизм продления ещё открыты.

## ADR-006 — Защита ключа резервных копий и политика полного восстановления снимка

- Дата: 2026-11-03
- Статус: УТВЕРЖДЕНО (только направление обработки ключа и политика восстановления)
- Контекст: Владелец выбрал защиту ключа локальных автоматических копий средствами Windows без отдельного пароля и дополнительного ключа восстановления. Владелец выбрал полное восстановление снимка после предварительного просмотра и создания копии текущих данных.
- Рассмотренные варианты: Для выбранного сценария отвергнуты отдельный пароль и дополнительный ключ восстановления. Выборочное восстановление не выбрано.
- Решение: Использовать защищённый Windows ключ для шифрования резервных копий без отдельного пароля и без предложения/создания дополнительного ключа восстановления в выбранном сценарии. Полный снимок восстанавливается только после предварительного просмотра и резервного копирования текущих данных. Восстановление затрагивает только содержимое в пределах данных архива; оно не сбрасывает пробный период/лицензию и не восстанавливает учётные данные OAuth или образ Windows. Сохранять подтверждение при удалении истории; не возвращать удалённую историю молча.
- Последствия: Нельзя гарантировать переносимость или восстановление без доступа к защищённому ключу. Не утверждать, что копии всегда работают только на том же компьютере: поведение роуминга Windows может различаться. Не выбраны API DPAPI, область/флаги защиты, шифр, KDF, место хранения/ротация ключа, формат архива, миграции и механизм восстановления после ошибки. Политика B3 определена: истечение 30-дневной истории не переписывает архивы; просроченная история хранится до окончания срока каждого архива (по умолчанию семь дней), при восстановлении применяется текущая целевая настройка срока истории. При явном удалении показывать затронутые архивы для пересоздания или удаления с подтверждением пользователя; не заявлять физическое удаление из всех копий через 30 дней. Доступность/формат архива, откат и точная механика истечения/восстановления остаются открытыми. Ежедневные и предструктурные/передмиграционные копии и настраиваемое хранение копий семь дней не меняются; копии включают историю; секреты и веса моделей в обычные копии не входят. Это решение не разрешает реализацию или использование API ОС.
- Основание согласования: Прямые решения владельца B2 и B3, 2026-11-03.

## ADR-007 — Ограниченные политики планировщика

- Дата: 2026-11-03, Europe/Moscow.
- Статус: утверждено владельцем; только поведение продукта.
- Контекст: планировщику нужны явные правила порядка допустимых задач, разрешения неоднозначности местного времени при переходе на летнее/зимнее время и обработки размещений после завершения сегментированного вхождения.
- Рассмотренные варианты: для порядка задач были предложены «сначала срок, затем приоритет», только приоритет или настраиваемый порядок; выбран сначала срок, затем приоритет. Молчаливый перенос времени при DST-пропуске и молчаливый выбор при DST-повторе исключены; владелец выбрал подтверждение ближайшего допустимого времени либо одного из двух моментов. При завершении выбранного вхождения освобождаются только его будущие размещения с сохранением истории.
- Решение: задачи с крайним сроком упорядочиваются сначала по ближайшему сроку, затем по приоритету. Задачи без срока упорядочиваются по приоритету. Для несуществующего местного времени в DST-пропуске предложить ближайшее допустимое время и запросить подтверждение; для повторяющегося времени в DST-повторе показать оба возможных момента и запросить подтверждение. При явном завершении вхождения освободить только оставшиеся будущие размещения этого выбранного вхождения и сохранить историю размещений.
- Последствия: правила не определяют разрешение равенств по сроку/приоритету, точные варианты «ближайшего» времени DST или их представление, действие для размещения, уже начавшегося, но ещё не завершившегося на момент выполнения, и поведение напоминаний. Они не утверждают алгоритм, схему, код или реализацию. Действие завершения остаётся отдельным от отметок сегментов; соседние вхождения не меняются.
- Основание согласования: Явные ответы владельца на карточки решений планировщика, 2026-11-03.

Для каждого согласованного решения указывай постоянный ID, дату, статус, контекст, рассмотренные варианты, выбранное решение, последствия и основание согласования владельцем. Поддерживай одинаковые ID и статусы с английской версией. До согласования отмечай предложения как предложенные; сохраняй заменённые решения со ссылками на новые.

## ADR-008 — Просроченные задачи, воздержание и завершение родителя

- Дата: 2026-11-04, Europe/Moscow.
- Статус: УТВЕРЖДЕНО (только поведение продукта).
- Контекст: Закрыть последние вопросы планера и привычек без неявного каскадного завершения.
- Рассмотренные варианты: Владелец выбрал доступность просроченного для планирования, явную отметку воздержания и сохранение активных подзадач при закрытии родителя вместо каскадного завершения.
- Решение:

Просроченные задачи остаются кандидатами автоматического предложения плана без изменения исходного срока и признака просрочки; применение предложения подчиняется действующим правилам подтверждения/разрешений. Успех воздержания требует явной отметки «соблюдено»; отсутствие отметки не считается успехом. Исправления по-прежнему разрешены за любую прошедшую дату существования привычки, с историей исправлений и целью, действовавшей в тот день.

При завершении родителя с незавершёнными подзадачами показывать «Закрыть задачу» и «Закончить подзадачи». «Закончить подзадачи» возвращает к списку подзадач без завершения родителя. «Закрыть задачу» завершает только выбранное вхождение родителя; подзадачи остаются активными и связанными, их собственные сроки и размещения сохраняются. Освобождаются только будущие размещения завершённого родителя с сохранением истории. Другие вхождения повторения не меняются. Явный выбор требуется и при отключённых обычных подтверждениях изменения задач: он определяет намерение пользователя.

На дату этого решения открытыми остаются точная схема, имена API, вложенность/наследование подзадач и обработка уже начавшихся размещений. Позже правила вложенности/наследования подзадач уточнены в ADR-009; обработка уже начавшихся размещений остаётся открытой. Эти продуктовые решения не разрешают реализацию.

- Основание согласования: Отправленные ответы владельца и оба уточнения завершения родителя, записанные в PLAN-013.

## ADR-009 — Измерения привычек и многоуровневые подзадачи

- Дата: 2026-11-04, Europe/Moscow.
- Статус: УТВЕРЖДЕНО (только поведение продукта).
- Контекст и варианты: Владелец выбрал режим количества отдельно для привычки вместо общего режима, таймер вместе с ручным вводом вместо одного из способов и многоуровневые подзадачи вместо фиксированного ограничения глубины.
- Решение и последствия:

- Для каждой количественной привычки выбирается режим: складывать отдельные порции (по умолчанию) или вводить общий итог дня. Ввод общего итога не является дополнительной порцией; исправления сохраняются в истории. Режим для привычки меняется сразу после показа предварительного пересчёта; текущий день пересчитывается по новому режиму, прошлые дни не меняются, история исправлений сохраняется. Единицы/пороги и точный механизм пересчёта ещё требуют проработки.
- Привычки на длительность поддерживают таймер с паузой и ручной ввод времени. Несколько занятий складываются за день. Запущенный таймер продолжает отсчёт во время сна компьютера, полного выхода из приложения и выключения компьютера, пока пользователь явно не поставит его на паузу или не остановит; при возобновлении приложение показывает прошедшее время. Разделять прошедшую длительность на местной полуночи, относя каждую часть к своему дню. Сохранение/сверка меток времени, смена часов, поездки между часовыми поясами, пересечение ручного ввода и сессий таймера и восстановление после сбоя остаются техническими вопросами. Двойной учёт нужно исключить.
- Подзадачи поддерживают несколько уровней без фиксированного продуктового ограничения глубины; интерфейс позволяет сворачивать ветки. Это не обещание бесконечной ёмкости устройства. Предотвращение циклов и загрузка больших деревьев — технические требования для рассмотрения. Для новой подзадачи предлагаются проект и приоритет родителя с обязательным явным подтверждением; срок ребёнка задаётся отдельно. Будущие изменения родителя не распространяются на существующих детей. Предотвращение циклов и загрузка больших деревьев остаются техническими вопросами; перенос веток и удаление — выбором владельца. Прежнее поведение завершения родителя сохраняется.

- Основание согласования: Три ответа владельца из PLAN-014 и последующие уточнения из PLAN-015 (2026-11-04). Схема, алгоритм выполнения и реализация не утверждены.

## ADR-010 — Лимит устройств лицензии, перенос и перевод часов назад

- Дата: 2026-11-04, Europe/Moscow.
- Статус: УТВЕРЖДЕНО (только поведение продукта).
- Контекст: ADR-005 оставил открытыми число устройств, поведение при переустановке/смене железа и допуск по часам. Сервера активации нет.
- Рассмотренные варианты: одно, два или три устройства; файл лицензии без привязки к железу, файл с привязкой и перевыпуском по запросу или привязка с ограниченным самостоятельным переносом; при переводе часов назад — допуск 48 часов и затем блокировка, только предупреждение или немедленная блокировка.
- Решение: Одна лицензия действует на трёх устройствах максимум, включая текущие ПК с Windows и будущее приложение для Android. Файл лицензии не привязан к железу: работает на любом устройстве, поэтому переустановка Windows или смена ПК не требуют перевыпуска; лимит устройств задаётся условиями лицензии и технически не проверяется. Если системные часы переведены назад более чем на 48 часов относительно последнего доверенного времени, которое видело приложение, платные функции блокируются со статусом «проверьте дату и время», пока часы не исправлены; меньшие сдвиги и смена часового пояса допускаются. Блокировка следует поведению ADR-005 для истёкшего доступа: данные, продление/импорт, удаление и бэкапы остаются доступны. Оплата пока вне объёма и будет проработана позже.
- Последствия: Передачу файла лицензии другим людям технически предотвратить нельзя; это принятый компромисс офлайн-модели без привязки к железу. Пробный период 7 дней на устройство остаётся как в ADR-005. Хранение доверенного времени, формат/подпись лицензии, инструменты выпуска, платёжный провайдер и цена остаются открытыми. Реализация не разрешена.
- Основание согласования: Ответы владельца в PLAN-018 (2026-11-04).

## ADR-011 — Свои персонажи вместо сторонних

- Дата: 2026-11-04, Europe/Moscow.
- Статус: УТВЕРЖДЕНО (только поведение продукта); заменяет требование использовать названных сторонних персонажей и их узнаваемые голоса.
- Контекст: Ранее запрошенные персонажи и их голоса принадлежат правообладателям и актёрам озвучки; коммерческий выпуск не может использовать их без лицензий.
- Рассмотренные варианты: лицензировать оригинальных персонажей и голоса, разрабатывая на нейтральном голосе; создать своих персонажей по мотивам архетипов; отложить голоса.
- Решение: Djarvis выпускается со своими оригинальными персонажами по мотивам архетипов (например, дворецкий, учёный, ИИ-помощник), со своими именами и голосами, без имён, образов и голосов актёров сторонних персонажей. Голоса — от локального синтеза речи, лицензии голоса и модели которого разрешают коммерческое использование, или из записей, сделанных с письменного согласия. Локальный файл `Vois/join-5tracks.mp3` остаётся локальным только как личный ориентир; он не используется как голос продукта или материал для синтеза.
- Последствия: Имена, характеры и выбор голосов персонажей — открытые решения владельца. Проверка прав в CP10 теперь охватывает лицензии моделей/голосов и согласие на запись. Wake-фразы по умолчанию — имена персонажей. Реализация не разрешена.
- Основание согласования: Ответ владельца в PLAN-019 (2026-11-04).

## ADR-012 — Веб-поиск с ключом пользователя; погода MET Norway

- Дата: 2026-11-04, Europe/Moscow.
- Статус: УТВЕРЖДЕНО (только поведение продукта).
- Контекст: Своего сервера нет, а коммерческие поисковые API требуют секретный ключ, который нельзя встраивать в клиент.
- Рассмотренные варианты: ключ пользователя; только открытие в браузере; свой сервер-посредник (нарушил бы правило «без своего сервера»). Для погоды: MET Norway, платный Open-Meteo, ключ пользователя.
- Решение: Встроенный веб-поиск использует ключ поискового API, который пользователь вводит в настройках и который хранится локально в защищённом виде; без ключа поиск открывается в браузере пользователя, и Djarvis результаты не читает. Погода — MET Norway Locationforecast с указанием источника и идентифицирующим User-Agent; город берётся из настройки пользователя и локального справочника городов. Цена и выпуск лицензий отложены вместе с оплатой.
- Последствия: Конкретный поисковый провайдер, хранение ключа, условия и атрибуция провайдеров, справочник городов и ограничения трафика проверяются до выпуска. Отправляются только явный запрос и выбранный город. Реализация не разрешена.
- Основание согласования: Ответы владельца в PLAN-019 (2026-11-04).

## ADR-013 — Персонажи, навигация, подтверждения действий с устройством, папка бэкапов

- Дата: 2026-11-04, Europe/Moscow.
- Статус: УТВЕРЖДЕНО (только поведение продукта).
- Контекст: ADR-011 оставил открытыми имена персонажей; навигация DD09, подтверждения действий с устройством помимо выключения/перезагрузки/выхода и путь бэкапов были открыты.
- Решение:
  - Персонажи (имена — они же wake-фразы по умолчанию): «Эдвард» — учтивый дворецкий с сухим юмором; «Профессор Вольт» — эксцентричный учёный, ироничный, но без грубости; «Нова» — спокойный ИИ-помощник с чёткими ответами. Голоса подбираются под характер каждого по ADR-011.
  - Боковая панель сверху вниз: Сегодня, Задачи, Календарь, Привычки, Проекты, Заметки; Настройки — отдельно в нижней служебной зоне.
  - Закрытие программ, перевод ПК в сон и блокировка требуют подтверждения — в дополнение к уже всегда подтверждаемым выключению, перезагрузке, выходу из системы, удалению и перезаписи файлов. Запуск выбранных пользователем программ и изменение громкости или яркости — без подтверждения.
  - Папка бэкапов по умолчанию: `Документы\Djarvis Backups`, меняется в настройках.
- Последствия: Конкретные голосовые модели, стилистика персонажей, проверка приложений/аргументов и обработка ошибок папки бэкапов остаются технической работой. Реализация не разрешена.
- Основание согласования: Ответы владельца в PLAN-019 (2026-11-04).

## ADR-014 — Движки синтеза речи, поисковый провайдер, защита рабочей базы

- Дата: 2026-11-04, Europe/Moscow.
- Статус: УТВЕРЖДЕНО (направление продукта и технологий; версии не выбраны).
- Контекст: ADR-011–013 требуют офлайн-голосов с коммерческой лицензией, поискового провайдера с ключом пользователя и уровня защиты рабочей базы. Исследование 2026-11-04: активный движок Piper перешёл на GPL-3.0 (репозиторий MIT архивирован), лицензии голосов различаются; модели Silero некоммерческие; Vosk TTS (русский, несколько голосов) и Kokoro-82M (английский и другие языки, без русского) публикуют веса под Apache-2.0.
- Рассмотренные варианты: Vosk TTS + Kokoro; Piper для обоих языков; дикторы по договору. Tavily, Brave или оба. Права Windows с подсказкой BitLocker, шифрование отдельных полей или только права.
- Решение: Русская речь — синтетические голоса Vosk TTS (предпочтительно голоса, не обученные на названном реальном дикторе); английская — Kokoro. Эдвард — низкий мужской голос (британский в английском); Профессор Вольт — второй мужской, быстрее и выше; Нова — синтетический женский голос. Встроенный веб-поиск поддерживает Tavily с ключом пользователя. Рабочая папка PostgreSQL доступна только учётной записи пользователя Windows, приложение рекомендует включить шифрование устройства BitLocker; архивы шифруются по ADR-006.
- Последствия: До выпуска проверить происхождение и лицензию каждого выбранного голоса, точные версии моделей и зависимость фонемизатора под GPL (например, espeak-ng) и способ её поставки; замерить скорость синтеза и память на целевом CPU с 8 ГиБ. Условия Tavily, атрибуция и лимиты проверяются до выпуска. Реализация не разрешена.
- Основание согласования: Ответы владельца в PLAN-020 (2026-11-04).

## ADR-015 — Технические решения T1–T6: связь, база, бэкапы, установщик, память, голос

- Дата: 2026-11-04, Europe/Moscow.
- Статус: УТВЕРЖДЕНО (технические решения; план реализации на чтении у владельца).
- Контекст: PLAN-022 закрыл открытые технические вопросы CP01–CP04, CP15 и CP18 и вынес на выбор владельца шесть решений ([технические детали](TECHNICAL_DESIGN.ru.md) §6) по результатам [проверок выполнимости](FEASIBILITY.ru.md).
- Рассмотренные варианты: T1 — значком владеет ядро и интерфейс выгружается при закрытии окна; интерфейс остаётся в трее; закрытие окна = выход. T2 — миграции только вперёд с бэкапом или с обратными миграциями. T3 — ключ под защитой Windows без пароля или с дополнительным паролем. T4 — подпись позже, облачная подпись сразу или EV-сертификат. T5 — выгрузка модели через 1, 5 или 15 минут. T6 — Vosk TTS 0.7 и 0.9.
- Решение:
  - T1: интерфейс и ядро связаны loopback HTTP + WebSocket с токеном запуска и проверкой `Host`/`Origin`. Закрытие окна прячет интерфейс в область уведомлений; значком владеет интерфейс; ядро — отдельный процесс.
  - T2: частный PostgreSQL 18, драйвер asyncpg, свой исполнитель миграций только вперёд; перед каждой миграцией автоматический бэкап, откат — восстановлением бэкапа.
  - T3: формат бэкапа DJB1 — tar, AES-256-GCM потоковыми кусками, ключ архива под DPAPI без пароля (в рамках ADR-006).
  - T4: установщик Inno Setup для пользователя без прав администратора; на время разработки и закрытых тестов без подписи; сертификат подписи кода — перед публичным выпуском.
  - T5: в профиле 8 ГиБ модель и синтез выгружаются через 5 минут простоя; значение настраивается.
  - T6: русский синтез — Vosk TTS 0.7 во всех профилях; 0.9 — возможный вариант повышенного качества для 16 ГБ+ позже.
- Последствия: Фоновая память в профиле 8 ГиБ ≈ 0,7 ГБ вместе с интерфейсом в трее; память интерфейса нужно замерить. Без подписи Windows SmartScreen предупреждает при установке на тестовых машинах. Программирование не начинается, пока структура не проработана полностью и владелец не получил полный отчёт о готовности к программированию. Реальные проверки (голосовой помощник, микрофон, отслеживание задач и т. д.) проводятся после программирования; проверки без кода — тоже позже (условие владельца, PLAN-023).
- Основание согласования: Ответы владельца в PLAN-023 (2026-11-04).
