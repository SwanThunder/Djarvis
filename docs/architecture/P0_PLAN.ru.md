## 1. Результат Ф0

Проверяемый каркас Windows-приложения: Flutter-интерфейс запускает отдельное Python-ядро из встроенной среды, ядро создаёт или открывает только свой частный кластер PostgreSQL, публикует локальный API с одноразовым токеном, интерфейс показывает версию и состояние, а полный выход штатно останавливает принадлежащие приложению процессы. Закрытие окна оставляет интерфейс в трее. Всё запускается из рабочей сборки без ручной установки Python или PostgreSQL. Это критерий уже утверждённой Ф0 из IMPLEMENTATION_PLAN §3; предметные функции добавляются последующими фазами.

## 2. Последовательность работ и файлы

| --- | --- | --- |
| 1. Каркас и зависимости | Создать утверждённые корни `core/`, `ui/`, `scripts/` и нужные части `packaging/`; зафиксировать версии и хеши зависимостей, настройки ruff/mypy/pytest и анализа Dart; настроить Windows CI на запросах на слияние до main (ADR-027) | Чистая сборка на Windows; инструменты запускаются из закреплённых зависимостей |
| 2. Встроенные среды | Скрипты сборки загружают проверенные архивы встроенного Python и PostgreSQL в локальный кэш сборки, собирают рабочую папку приложения без внесения двоичных пакетов и пользовательских данных в Git | Встроенный Python и двоичные файлы PostgreSQL запускаются из рабочей папки без системных установок; старт ядра проверяется после шага 3 |

| 5. Оболочка главного экрана | `ui/lib/app`, `ui/lib/data`, `ui/lib/generated`: запуск/переподключение, оболочка утверждённого главного экрана с персонажем, панелью дня, навигацией и состоянием/версией ядра; значок трея, повторное открытие и полный выход (ADR-031) | Окно показывает оболочку без ещё не реализованных предметных функций; скрывается в трей, ядро остаётся работать, полный выход останавливает его и свою базу |
| 6. Проверка и фиксация | `core/tests`, `ui/test`, Windows CI, двуязычные README/документация и общий журнал | Линтеры, анализ, контрактные и стартовые проверки зелёные; владелец принимает Ф0 по записи экрана (ADR-032) |

Решение по CI для шага 1: проверки выполняются в запросе на слияние до main (ADR-027). В Ф0 к обязательным проверкам относятся ruff, строгий mypy, pytest для существующего кода, dart analyze, проверка генерации контракта и доступные Windows smoke-проверки; набор включается по мере появления соответствующих модулей, а не имитируется пустыми тестами. Проверки перед слиянием требуют настройки правил ветки; это будет сделано только после разрешения Ф0.

Шаг 2 принят владельцем (ADR-028): встроенные Python/PostgreSQL входят в сборку, архивы проверяются по закреплённым хешам, модели ИИ загружаются отдельно при первом запуске; программные файлы и данные пользователя разнесены.

Шаг 3 принят владельцем при условии (ADR-029): частной базой управляет приложение в фоне, без консольного окна и ручных действий. Интерфейс показывает только обычную загрузку или понятную ошибку восстановления; данные сохраняются после выхода.

Шаг 4 принят владельцем (ADR-030): в каркасе реально работают защищённое локальное соединение, `GetSystemStatus`, `RequestExit`, обработка ошибок/версий и генерация типов Flutter из Python-контракта. Остальные команды API появляются в следующих фазах.

Шаг 5 принят владельцем (ADR-031): Ф0 показывает оболочку будущего главного экрана по утверждённому дизайну, а не отдельный компактный экран состояния. Персонаж, панель дня и навигация задают компоновку; пока данные и действия разделов не реализованы, они явно выглядят недоступными или пустыми, без фиктивных задач, привычек и работающих кнопок. Реальные состояние и версия ядра видны в этой оболочке. Закрытие окна, повторное открытие из трея и полный выход работают по описанному жизненному циклу.

Шаг 6 принят владельцем (ADR-032): каждый шаг Ф0 — отдельный запрос на слияние; правило ветки запрещает слияние в main при непройденных проверках; разработчик сливает запрос только после явного «да» владельца. Ф0 принимается по записи экрана: запуск без системных Python/PostgreSQL, оболочка с состоянием и версией ядра, трей и повторное открытие, отсутствие второго ядра, полный выход. Запись не содержит токенов, паролей и личных данных.

Полный набор каталогов остаётся в IMPLEMENTATION_PLAN §2. В Ф0 контракт ограничен рабочим состоянием системы и жизненным циклом; полный каталог команд и миграция `0001_initial` реализуются в Ф1. Скрипты Ф0 собирают минимальную рабочую папку, а полноценный установщик и подпись относятся к Ф7.

## 3. Запуск и завершение

1. Интерфейс ищет живое ядро текущей учётной записи по мьютексу и проверяемому файлу подключения; если его нет, запускает встроенный Python-хост.
2. Хост без консольного окна проверяет частные каталоги и права, определяет принадлежность существующего кластера, инициализирует только новый кластер и запускает только принадлежащий ему PostgreSQL. Затем открывает API на `127.0.0.1` со случайным портом и новым токеном.
3. Интерфейс подключается по токену, проверяет версию протокола и показывает результат `GetSystemStatus`. После сбоя соединения он показывает восстановимое состояние с действием «Повторить»; второе окно не создаёт второе ядро/кластер.
4. Закрытие окна скрывает его в трей. «Полный выход» вызывает `RequestExit`: ядро останавливает API, закрывает соединения и штатно останавливает только собственный PostgreSQL; интерфейс завершается.

Подробная идемпотентность предметных команд, ревизии, планировщик, миграции схемы, голос и внешние интеграции предусмотрены утверждёнными следующими фазами. Ф0 создаёт настоящие границы и жизненный цикл, без фиктивных обработчиков предметных команд.

## 4. Сбои и сохранность

- Время ожидания запуска ядра ограничено 15 секундами; ожидание готовности базы — 10 секундами (TECHNICAL_DESIGN §1–2). Ошибка показывается в интерфейсе с повтором и локальной диагностикой, без бесконечного автоматического перезапуска.
- При занятом порте ядро выбирает другой свободный локальный порт. Неверный/чужой кластер, несоответствие владельца процесса или повреждённый файл состояния дают восстановимое состояние; ядро не удаляет и не перезаписывает чужие данные.
- Для проверок Ф0 используется отдельный временный частный кластер. До любого изменения существующих пользовательских данных в будущих фазах требуется бэкап с проверяемым восстановлением. Существующие локальные материалы проекта не переносятся и не очищаются.
- Токен и пароли не печатаются в журнал и не публикуются. Файл подключения и папка базы доступны только учётной записи Windows владельца; процесс PostgreSQL запускается с ограниченным набором локальных адресов и SCRAM-аутентификацией (TECHNICAL_DESIGN §2).

## 5. Приёмка Ф0

1. На Windows 10/11 рабочая сборка запускается без системного Python/PostgreSQL и без прав администратора; ядро из встроенной среды поднимает и останавливает свою базу.
2. Интерфейс подключается по одноразовому токену, показывает версию ядра и состояние базы. Неверный токен, `Host`, HTTP `Origin` и версия протокола обрабатываются определённым образом.
3. Повторный запуск интерфейса не создаёт второе ядро/кластер; закрытие окна оставляет трей и ядро, полный выход их завершает. После сбоя интерфейса повторное подключение работает.
4. Проверки Python/Dart, генерации контракта и Windows CI проходят. Результат показывается владельцу записью экрана (ADR-032); переход к Ф1 требует приёмки Ф0 по утверждённому плану.

## 6. Следующее решение

Все шесть шагов плана обсуждены и приняты владельцем (ADR-027–032). Владелец разрешил Ф0 в объёме этого плана 2026-11-05 (ADR-033). Шаг 1 выполнен (PLAN-045) и идёт отдельным запросом на слияние по ADR-032; прогон CI и сборка Djarvis.exe проверяются в этом запросе, а слияние — только после явного «да» владельца. Следующий — шаг 2 «Встроенные среды» (ADR-028). Шаги выполняются по порядку, каждый отдельным запросом на слияние; переход к Ф1 — только после приёмки Ф0 владельцем по записи экрана (§5, ADR-032).
