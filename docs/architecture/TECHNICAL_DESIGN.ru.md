## 1. Связь интерфейса с ядром

### 1.1 Процессы и кто кого запускает

| Процесс | Что это | Владеет |
| --- | --- | --- |
| `Djarvis.exe` | Интерфейс Flutter | Окна, ввод, отображение, значок в области уведомлений. Нет доступа к базе и секретам |
| `djarvis-core.exe` | Встроенный Python 3.12 (переименованный запускатель официального пакета embeddable, режим `-I`) | Все команды, политика, планировщик, база, напоминания и звук; значком в области уведомлений владеет интерфейс |
| `postgres.exe` | Частный PostgreSQL 18 | Только данные; запускает и останавливает ядро |
| `djarvis-llm.exe` | Сервер llama.cpp (MIT) | Языковая модель; запускается ядром по требованию и выгружается при простое |
| речевые рабочие | Потоки или подпроцессы ядра (Vosk, Kokoro, Vosk TTS) | Только вычисления; в базу не пишут |

Порядок запуска. `Djarvis.exe` проверяет именованный мьютекс ядра текущего пользователя. Если ядро не запущено, интерфейс запускает его и ждёт файла подключения не дольше 15 секунд, показывая экран запуска. Закрытие окна только прячет его: процесс интерфейса остаётся в области уведомлений (решение владельца T1, ADR-015), ядро, ожидание ключевой фразы и напоминания продолжают работать. Значком владеет интерфейс (плагин трея Flutter с разрешительной лицензией); щелчок по значку снова показывает окно. Ядро — отдельный процесс и не зависит от интерфейса: если интерфейс упал, ядро продолжает работу, а значок появляется снова при следующем запуске `Djarvis.exe` (автозапуск при входе в Windows). Пункт «Выход» останавливает всё в порядке из CP01.

### 1.2 Транспорт

- HTTP/1.1 для команд и запросов, WebSocket для событий. Ядро слушает только `127.0.0.1` на случайном свободном порту.
- Python: `aiohttp` (Apache-2.0) — одна библиотека для сервера HTTP и WebSocket и для клиента к модели и внешним сервисам. Flutter: `http` и `web_socket_channel` (BSD).
- Файл подключения `%LOCALAPPDATA%\Djarvis\run\endpoint.json`: порт, одноразовый токен запуска (32 случайных байта), PID и идентификатор экземпляра ядра. Права на файл — только владелец (явный ACL, как для папки базы). Файл перезаписывается при каждом запуске ядра и удаляется при выходе.
- Проверки на каждом запросе: заголовок `Authorization: Bearer <токен>`; `Host` строго равен `127.0.0.1:<порт>` (защита от DNS-rebinding); запрос с заголовком `Origin` отклоняется, чтобы страницы браузера не могли обратиться к ядру. WebSocket передаёт токен первым сообщением, а не в URL. Токен не попадает в журналы.
- Версии: путь `/v1/...` и поле `protocol_version` в конверте. Ядро поддерживает текущую и предыдущую версию протокола. Интерфейс несовместимой версии получает понятную ошибку «обновите приложение».

### 1.3 Формат сообщений и контракт

- JSON в UTF-8; конверт и состояния результата — из CP01 §2.3 (`AppliedLocal`, `NeedsConfirmation`, `Conflict` и т. д.).
- Время всегда передаётся явно: мгновение — RFC 3339 с `Z`; местное намерение — дата, время и имя зоны IANA отдельными полями.
- Источник истины контракта — модели Pydantic v2 (MIT) в ядре. Сборка выгружает из них JSON Schema; классы Dart генерирует скрипт проекта. Проверка в CI падает, если сгенерированный код устарел. Ручное дублирование типов в Dart запрещено.
- События WebSocket: `{"type": "changed", "revision": N, "resources": [...]}`. Это лишь подсказка перечитать данные. При разрыве или пропуске ревизии интерфейс запрашивает свежий снимок (CP01 §2.4).
- Ошибки: код из закрытого перечня, текст для пользователя на языке интерфейса и `request_id` для локальной диагностики. Трассировки стека интерфейсу не передаются.

### 1.4 Почему не именованный канал

Именованный канал Windows не открывает порт, но клиент Flutter для него потребовал бы собственного нативного кода, а будущему Android всё равно нужен другой транспорт. Риски loopback-порта закрыты токеном, проверкой `Host` и `Origin` и ACL файла подключения. Защиты от вредоносной программы, запущенной под той же учётной записью Windows, нет ни у одного из двух вариантов (CP01).

## 2. База данных: схема и миграции

### 2.1 Экземпляр PostgreSQL

- Поставка: zip-бинарники PostgreSQL 18.x для Windows, только `bin`, `lib`, `share` (≈ 141 МБ из 328 МБ, PLAN-021).
- Кластер: `%LOCALAPPDATA%\Djarvis\db\pg18`, явный ACL только для владельца. `initdb --encoding=UTF8 --locale-provider=builtin --builtin-locale=C.UTF-8 --auth=scram-sha-256`. Встроенный провайдер локали не зависит от версий ICU и Windows, поэтому обновление системы не ломает индексы. Сортировку по алфавиту для экрана задаёт явная ICU-коллация в конкретном запросе.
- Сеть: `listen_addresses = '127.0.0.1'`, случайный порт; в `pg_hba.conf` только `host … 127.0.0.1/32 scram-sha-256`, без `trust`.
- Роли: `djarvis_owner` владеет схемой и выполняет миграции; `djarvis_app` получает только DML на таблицы схемы `app`. Пароли — по 32 случайных байта под DPAPI в области пользователя; в файлы и журналы не попадают.
- Настройки для 8 ГиБ: `shared_buffers = 64MB`, `work_mem = 4MB`, `max_connections = 10`, `jit = off`, `autovacuum = on`.
- Запуск: `pg_ctl start` с выводом в файл журнала, не в канал (вывод 6 из PLAN-021). Готовность проверяется подключением с повторами до 10 секунд.

### 2.2 Драйвер

`asyncpg` (Apache-2.0): асинхронный драйвер, совместимый с `aiohttp`. Пул из 2–4 соединений. ORM нет: SQL лежит в модулях репозиториев по областям и проверяется тестами на реальном PostgreSQL. psycopg 3 не выбран из-за лицензии LGPL-3.0 и лишнего слоя совместимости.

### 2.3 Схема (версия 1)

Ниже сохранён ранний концептуальный пример, а не актуальный перечень полей и таблиц. Для реализации и согласования схемы использовать [SCHEMA](SCHEMA.ru.md): это утверждённая логическая схема из 46 таблиц (ADR-024).

Общие правила:

- Ключи — UUIDv7 (`uuidv7()` есть в PostgreSQL 18): упорядочены по времени, подходят для будущей синхронизации.
- Каждая изменяемая запись имеет `profile_id`, `revision bigint` (растёт при каждом изменении), `created_at` и `updated_at` (`timestamptz`).
- Мгновения хранятся в `timestamptz`; намерения пользователя — `local_date`, `local_time` и `tz text` (IANA) отдельными полями (CP06).
- Перечисления — `text` с `CHECK` (их легче мигрировать, чем `ENUM`).
- Удаление пользовательских данных — физическое с каскадом, кроме случаев, где история нужна по ADR (выполненные вхождения, журнал привычек).

Таблицы по группам:

| Группа | Таблицы |
| --- | --- |
| Профиль и настройки | `profile`, `setting` (ключ, значение JSON, ревизия), `availability_rule` |
| Задачи | `task` (`parent_id` для многоуровневых подзадач, приоритет обязателен, `deadline_*`), `task_occurrence`, `schedule_placement`, `split_mark`, `recurrence_rule`, `recurrence_exception` |
| Привычки | `habit`, `habit_schedule` (действует с даты), `habit_pause`, `habit_measurement`, `timer_session` (переживает сон и выключение, делится в полночь — ADR-009) |
| Календарь | `calendar_event`, `provider_account`, `provider_mapping`, `sync_cursor`, `sync_conflict` |
| План дня | `planning_guard` (одна строка на профиль, ревизия планирования), `day_plan_proposal`, `day_plan_item` |
| Проекты и заметки | `project`, `note`, `tag`, `note_tag`, `task_tag`, `attachment` (sha256, размер, путь в хранилище; файл неизменяем) |
| Действия и политика | `processed_action`, `approval_request`, `capability_grant`, `outbox`, `audit_event` (метаданные без содержимого) |
| Ассистент | `reminder`, `reminder_delivery`, `conversation_message` (хранение 30 дней по умолчанию), `deletion_watermark` |
| Служебные | `schema_migration`, `backup_record` |

Пример ключевых таблиц (иллюстрация уровня детализации; окончательный DDL пишется в фазе 1 вместе с тестами):

```sql
CREATE TABLE app.task (
  id            uuid PRIMARY KEY DEFAULT uuidv7(),
  profile_id    uuid NOT NULL REFERENCES app.profile(id) ON DELETE CASCADE,
  parent_id     uuid REFERENCES app.task(id) ON DELETE CASCADE,
  project_id    uuid REFERENCES app.project(id) ON DELETE SET NULL,
  title         text NOT NULL CHECK (length(btrim(title)) > 0),
  priority      text NOT NULL CHECK (priority IN ('low','normal','high','critical')),
  deadline_date date,
  deadline_time time,
  deadline_tz   text,
  estimate_min  integer CHECK (estimate_min > 0),
  state         text NOT NULL DEFAULT 'open' CHECK (state IN ('open','done','cancelled')),
  completed_at  timestamptz,
  revision      bigint NOT NULL DEFAULT 1,
  created_at    timestamptz NOT NULL DEFAULT now(),
  updated_at    timestamptz NOT NULL DEFAULT now(),
  CHECK ((state = 'done') = (completed_at IS NOT NULL)),
  CHECK (deadline_time IS NULL OR deadline_date IS NOT NULL)
);
CREATE INDEX task_open_deadline ON app.task (profile_id, deadline_date) WHERE state = 'open';

CREATE TABLE app.processed_action (
  profile_id   uuid NOT NULL,
  action_id    text NOT NULL,
  request_hash bytea NOT NULL,
  result       jsonb NOT NULL,
  created_at   timestamptz NOT NULL DEFAULT now(),
  PRIMARY KEY (profile_id, action_id)
);
```

Глубину вложенности подзадач и отсутствие циклов проверяет ядро в транзакции команды; `CHECK` между строками в PostgreSQL выразить нельзя.

### 2.4 Миграции

- Свой небольшой исполнитель вместо Alembic: Alembic тянет SQLAlchemy ради одной функции.
- Файлы `core/migrations/NNNN_описание.sql`; для преобразования данных — парный `NNNN_описание.py` с функцией `apply(conn)`.
- Таблица `schema_migration(id, checksum sha256, applied_at, app_version)`. Перед запуском ядро сверяет контрольные суммы уже применённых миграций; расхождение означает `RecoveryRequired`, без попытки «починить».
- Порядок: проверка места на диске → бэкап перед миграцией (ADR-006; провал бэкапа отменяет миграцию) → режим обслуживания (новые команды получают `Unavailable`) → каждая миграция в своей транзакции под `djarvis_owner` → проверка инвариантов → публикация новой версии схемы.
- Только вперёд. Откат — восстановление бэкапа, сделанного перед миграцией, вместе с прежней версией программы (CP18).
- Старая программа не открывает схему новее себя: она сравнивает максимальный известный ей `id` миграции.
- Мажорное обновление PostgreSQL (18 → 19) — отдельная процедура через `pg_dump` и восстановление в новый кластер, а не миграция схемы.

## 3. Шифрование бэкапов

Принято в ADR-006: ключ под защитой Windows, без пароля и без ключа восстановления; ежедневно и перед миграциями; хранение 7 дней. Ниже — конкретный формат на основе предложений DD02 и DD03.

### 3.1 Содержимое

Контейнер DJB1 (T3, ADR-015) сохраняется; меняется только проект логического наполнения. До шифрования архив — tar:

- `manifest.json`: версии формата, схемы, программы и набора выгрузки, время снимка, число записей и контрольные суммы вложений;
- `db.data`: согласованный набор пользовательских строк из схемы `app`, выгруженный из одного согласованного снимка транзакции; перечень таблиц в [SCHEMA §13](SCHEMA.ru.md#13-состав-архива-и-восстановление-adr-023);
- `blobs/<sha256>`: вложения, на которые ссылаются выбранные строки.

Полный `pg_dump --schema=app` из прежней версии проекта **не соответствует ADR-023**: он включил бы разрешения, внешние подключения, неподтверждённые запросы и очередь писем. Экспорт v1 выполняется по закрытому списку таблиц; схема промежуточной базы создаётся из подходящих версий миграций, после чего импортируются выбранные строки. Дамп не содержит лицензии/триала, токенов OAuth, секретов IPC, весов моделей, кэшей, разрешений, внешних подключений и очередей. Точный механизм потоковой выгрузки определяется в фазе реализации и проверяется на настоящем PostgreSQL; старая команда не используется.

### 3.2 Шифрованный контейнер «DJB1»

| Часть | Содержимое |
| --- | --- |
| Заголовок (открытый) | магия `DJB1`, версия формата, `archive_id` (16 случайных байт), размер куска, идентификатор способа обёртки ключа (`dpapi-user-v1`) |
| Обёрнутый ключ | 256-битный ключ архива под `CryptProtectData` (область пользователя, без интерфейсных запросов, с постоянной дополнительной энтропией продукта) |
| Куски | по 1 МиБ открытого текста; AES-256-GCM (`cryptography`, Apache-2.0/BSD); nonce = 64-битный счётчик куска + 32 бита флагов, флаг `last` только у последнего куска (схема STREAM); AAD = SHA-256 заголовка |
| Итог | последний кусок содержит длину и число кусков; обрезка, перестановка и подмена кусков отвергаются |

- Ключ новый для каждого архива, поэтому счётчик в nonce никогда не повторяется под одним ключом. Производная от пароля (KDF) не нужна.
- Запись идёт во временный файл в той же папке и атомарно переименовывается после проверки. Незавершённый архив никогда не выглядит успешным.
- DPAPI вызывается через ctypes собственным кодом (≈ 50 строк), без pywin32.
- Перед реализацией: эталонные векторы (шифрование и расшифровка известного архива), тесты на обрезку, перестановку, подмену заголовка и чужой ключ.
- Ограничение остаётся (ADR-006): если доступ к ключу DPAPI потерян (например, администратор сбросил пароль Windows), архив не расшифровать. Это показывается пользователю при первом бэкапе.

### 3.3 Восстановление

Последовательность: `Выбран → Подлинность → Проверен → Предпросмотр → Бэкап текущих данных → Восстановление в промежуточную базу → Проверка → Переключение → Готово`. Промежуточная база `djarvis_restore` создаётся в том же кластере; переключение — переименование баз в режиме обслуживания с маркером операции на диске. До переключения ядро проверяет ссылки, применяет текущий срок хранения истории и более позднюю из текущей и архивной отметок удаления истории (ADR-006).

По ADR-023 в промежуточную базу не импортируются прежние разрешения, цели запуска программ, учётные записи/карты внешних календарей, ожидающие подтверждения, отправки писем и другие внешние очереди. Неактивные черновики плана становятся `stale`; сохранённые временные блоки и история выполнения остаются. Настройки инициативной речи и автопрослушивания сбрасываются до явной новой настройки. Правила напоминаний сохраняются, но очередь заданий строится заново из актуальных данных; старые задания и письма не воспроизводятся. События из отключённых внешних календарей показываются как локальные снимки без автоматической синхронизации до нового подключения и согласования сопоставления. Лицензия/триал и секреты OAuth не заменяются восстановлением.

## 4. Установщик

- **Inno Setup** (бесплатен, разрешительная лицензия, допускает коммерческое использование): установка для текущего пользователя без прав администратора в `%LOCALAPPDATA%\Programs\Djarvis`. MSIX отклонён: его виртуализация файлов и реестра мешает частному PostgreSQL и фоновому ядру (DD06).
- Корни (CP18): программа — `%LOCALAPPDATA%\Programs\Djarvis`; данные — `%LOCALAPPDATA%\Djarvis\{db,files,run,logs,models,cache}`; бэкапы — `Документы\Djarvis Backups` (ADR-013).
- Состав установщика: интерфейс Flutter, встроенный Python с закреплёнными пакетами (`pip install --target` с проверкой хешей из файла блокировки), урезанный PostgreSQL, сервер llama.cpp, Vosk и onnxruntime. Ожидаемый размер — 250–350 МБ; уточняется в фазе 7.
- Модели в установщик не входят. Первый запуск скачивает их по подписанному манифесту ресурсов (CP18) с прогрессом, паузой и докачкой: языковая модель ≈ 2,7 ГБ; Vosk small ru и en ≈ 0,16 ГБ; Vosk TTS 0.7 ≈ 0,13 ГБ; Kokoro и голоса ≈ 0,12 ГБ. Всего ≈ 3,1 ГБ. Без моделей планировщик работает, а ассистент честно показывает «ресурсы загружаются».
- Подпись: все EXE и DLL продукта и установщик. Нужен сертификат подписи кода — решение владельца по стоимости (OV, EV или облачная подпись). Без подписи Windows SmartScreen будет предупреждать при установке.
- Обновления (DD07): только уведомление; скачивание и установка — по команде пользователя. Установщик в режиме обновления останавливает ядро, сохраняет прежнюю версию до проверки здоровья, затем ядро выполняет миграции с бэкапом.
- Удаление: программа удаляется; данные и бэкапы по умолчанию сохраняются; удаление данных — отдельный подтверждаемый флажок. Следы триала не стираются.

## 5. Профиль для 8 ГиБ

Бюджет по замерам PLAN-021 и PLAN-022 (рабочий набор; интерфейс Flutter ещё не замерен):

| Компонент | Когда загружен | Память |
| --- | --- | --- |
| Ядро Python | всегда | ≈ 0,1 ГБ |
| PostgreSQL | всегда | ≈ 0,2 ГБ |
| Vosk small текущего языка (ключевая фраза и реплика) | пока микрофон включён | ≈ 0,2 ГБ |
| Интерфейс Flutter (в трее, когда окно закрыто) | всегда | ≈ 0,2 ГБ (оценка; замерить) |
| Языковая модель 4B Q4_K_M, контекст 4096 | по требованию, выгрузка при простое | ≈ 3,0 ГБ |
| Синтез текущего языка: Vosk TTS 0.7 (ru) или Kokoro (en) | вместе с моделью | 0,75 ГБ или ≈ 0,3 ГБ |
| **Пик в диалоге (ru, окно открыто)** | | **≈ 4,45 ГБ** |
| Фон с закрытым окном | | ≈ 0,7 ГБ |

Правила профиля:

1. В фоне загружено только постоянное (≈ 0,7 ГБ вместе с интерфейсом в трее). Языковая модель и синтез загружаются по требованию.
2. Загрузка модели начинается сразу при срабатывании ключевой фразы, параллельно с записью реплики, и скрывает ≈ 5 секунд загрузки. Веса отображаются в память (mmap), поэтому повторная загрузка из кэша Windows быстрее.
3. Выгрузка модели и синтеза через 5 минут простоя (настраивается: 1–30 минут или «не выгружать»). Выгрузка — остановка процесса `djarvis-llm.exe`.
4. Загружается только синтез языка ответа; второй язык подгружается, лишь когда нужен.
5. Whisper и Vosk TTS 0.9 в этом профиле не загружаются.
6. Перед загрузкой модели ядро проверяет свободную память (`GlobalMemoryStatusEx`). Если её меньше 3,6 ГБ, ассистент отвечает текстом без синтеза. Если меньше 3,0 ГБ, он честно сообщает о нехватке памяти и предлагает закрыть программы; облачной подмены нет.
7. Потоки модели — число физических ядер минус одно; синтез ответа идёт по предложениям по мере генерации (вывод 2 PLAN-021).
8. Профиль выбирается автоматически по объёму ОЗУ: ≤ 12 ГиБ — «8 ГБ»; больше — «16 ГБ+». В «16 ГБ+» модель держится 30 минут, допускается Vosk TTS 0.9 и второй проход Whisper small.

Открыто: замер на реальной машине с 8 ГиБ (Windows 11 с браузером обычно занимает 3–4 ГБ, поэтому запас около 0,5–1 ГБ) и выбор запасной меньшей модели (класса 1,5–2 ГБ) с проверкой качества на русском.
