## 1. Кто за что отвечает

| Слой | Модули | Ответственность |
| --- | --- | --- |
| Чистая предметная логика | `domain.tasks`, `.recurrence`, `.time`, `.planner`, `.habits`, `.policy` | Правила задач, повторов, времени, плана дня, привычек и доступа без базы, сети, файлов и системных часов |
| Сценарии приложения | `app.commands`, `.queries`, `.approvals`, `.ports` | Единый путь изменения данных, чтение для экранов, точные подтверждения, интерфейсы к внешнему миру |
| Данные и локальная база | `storage`, `db` | Транзакции/репозитории/вложения и отдельный жизненный цикл частного PostgreSQL |
| Входы | `api`, `assistant`, `audio`, `reminders` | HTTP/WebSocket, ограниченные инструменты модели, единственный владелец микрофона, напоминания и инициативная речь |
| Адаптеры и доверие | `integrations.*`, `safety.backup`, `safety.entitlement` | Подключения к сервисам/Windows, архив и восстановление, локальная проверка доступа |
| Сборка и интерфейс | `host`, Flutter `ui/app`, `ui/data`, `ui/features/*` | Запуск и соединение компонентов; экраны отображают результаты ядра |

## 2. Правило зависимостей

`api`, `assistant` и `reminders` вызывают `app`; все изменения проходят через его конвейер. `app` использует чистый `domain` и интерфейсы `app.ports`. `storage`, `integrations`, `audio` и `safety` реализуют эти интерфейсы; их конкретные классы собирает только `host`. Интерфейс Flutter не принимает решений о правах или выполнении дела. Проверка направлений импорта предусмотрена в CI.

В одном процессе Python работает цикл `asyncio`; распознавание и синтез вынесены из цикла, языковая модель запускается отдельным процессом. Транзакция не ждёт ответа человека, модели или сети. После сбоя голоса планировщик и интерфейс продолжают работать; при выходе ядро останавливает захват, задания, модель и свой PostgreSQL в заданном порядке.

## 3. Сверка с утверждёнными контрактами

- `api` назначает источник команды по вызывающему процессу; `app.approvals` связывает подтверждение с действием, вызывающим процессом, точным содержимым и ревизиями (ADR-025).
- `safety.backup` выгружает только таблицы из SCHEMA §13. После восстановления прежние разрешения/подключения/очереди не возобновляются (ADR-023–024).
- `integrations.google` отвечает за Gmail; обе календарные интеграции работают через локальную очередь. Письмо с неизвестным итогом не повторяется автоматически, ручной повтор требует нового подтверждения.
- `assistant` и `reminders` получают данные и выполняют действия через `app`, не пишут в базу обходным путём. Цель для задержки цикла — 50 мс, нарушения фиксируются сторожевым таймером при разработке.

Эти уточнения утверждены в составе ADR-026 и внесены в MODULES. Они не меняют утверждённый API и схему.

## 4. Проверки и порядок реализации

Ф0 создаёт каркас `host`, `db`, `api`, `contract` и соединение с UI. Ф1 реализует транзакционный путь `app`/`storage`; Ф2 — чистый планировщик; Ф3 — экраны; Ф4 — бэкап и доступ; Ф5 — голос; Ф6 — внешние подключения; Ф7 — поставку. Зависимости и критерии фаз утверждены отдельно (ADR-018). Для модулей предусмотрены unit/property, контрактные, интеграционные на настоящем PostgreSQL, widget/golden и ручные голосовые проверки после программирования.
